    Data-driven tests

    Run one test with many sets of values, such as several users, languages or products, from a table in a CSV file.

    On this page

    • How it works
    • An example
    • Once per row
    • Choosing rows

    How it works

    Put the values in a CSV file next to the test: one row per set of values and one column per value. Add a useData block that names the file. Blocks after it read the current row's values as ${data.COLUMN}, where COLUMN is the name in the first line of the file.

    An example

    data/accounts.csv:

    name,email,password
Anna,anna@example.com,first-try
Bo,bo@example.com,"quotes ""inside"", and a comma"

    The test:

    {
  "format": 1,
  "name": "Sign in",
  "app": "com.example.AcmeMail",
  "start": "open",
  "blocks": {
    "open":     { "type": "openApp", "next": "accounts" },
    "accounts": { "type": "useData", "file": "data/accounts.csv", "body": "email" },
    "email":    { "type": "type", "text": "${data.email}", "into": { "image": "refs/email-field.png" }, "next": "password" },
    "password": { "type": "type", "text": "${data.password}", "into": { "image": "refs/password-field.png" }, "next": "inbox" },
    "inbox":    { "type": "waitFor", "until": { "appears": { "image": "refs/inbox.png" } }, "next": "accounts" }
  }
}

    The last block of the body, inbox, leads back to accounts, as every loop body does.

    Once per row

    The first useData block on the way from start names the test's table. The whole test runs once for each of its rows, and every block of the test reads that row's values.

    • Each row is a result of its own, with its own retries. The report keeps which row ran, and flaky tests and quarantine suggestions are worked out row by row: a row that fails now and then is flaky, the others aren't.
    • A row is named by its name column (in any case, such as Name), or else by its first column: “Row 2: Bo”.
    • The run passes when every row passes. The report and the run summary say how many did, such as “4 of 5 rows passed”.
    • In JUnit XML, each row is a test case of its own, such as Sign in [Row 2: Bo].

    Choosing rows

    All rows run by default. To run some of them:

    • Command line: jevision run tests/sign-in.flow.json --row 3 or --rows 2-4.
    • App: the Run menu, which picks one row or all of them for the next runs.
    • AI assistant: rows of run_test, such as "2" or "2-4".

    Rows count from 1; the header line isn't a row. Asking for a row the table doesn't have stops the run before it starts.

    CSV rules

    JEVision reads CSV as described in RFC 4180, the format spreadsheet apps export:

    • The first line names the columns. Every name must be filled in and different from the others.
    • Values are separated by ,, ; or a tab, whichever the first line uses most. Spreadsheets in many languages export ;, and that works as is.
    • A value with the separator, a quote or a line break goes in double quotes, with a quote inside written twice ("").
    • Every line has as many values as the header. A value may be empty.
    • Blank lines are skipped.
    • The file is UTF-8, with or without a byte order mark, with LF or CR LF line ends.

    The editor and jevision validate report a table that breaks these rules, with the line where it goes wrong, and a ${data.COLUMN} that the table doesn't have, with the columns it does have.

    Loops inside a run

    Only the first useData table runs the whole test per row. Two kinds of tables loop through their rows inside one run instead, like a repeat block:

    • a table whose path holds a placeholder, such as data/${env.REGION}.csv;
    • any further useData block of the test.

    Editing the table in the app

    Select the useData block and click Edit Data… to see the table, change cells, and add or remove rows and columns. Saving keeps the file's separator, line ends and byte order mark, so the diff shows only what you changed.
