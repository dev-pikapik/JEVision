    Custom blocks

    A custom block is a few steps with a name, ready to use in any test, such as “Sign in”. Make your own, hand them to a colleague, or install blocks that other people shared.

    What a custom block is

    A custom block is a test that other tests run as one step, with the runTest block. It can ask for values, so one block serves many tests: the sign-in block asks for an email and a password, and each test says which.

    There are two kinds, and both show up in the block library and in the Test menu of a runTest block:

    • Your blocks are files in the blocks folder of your project, such as blocks/Sign in.block.json. You made them.
    • Blocks from the community are packages other people made, installed into the blocks folder of your project. The library lists them in the group Community, with their author and version.

    Using a block in a test

    Add a block from the library (Space on the canvas, or ⌘K), or add a runTest block and choose the custom block as its test. Fill in the values it asks for. A value may hold ${env.NAME}, ${secret.NAME} and ${data.COLUMN} of the test that uses the block.

    {
  "type": "runTest",
  "test": "blocks/com.acme.sign-in.jevblock/flow.json",
  "package": { "version": "1.2.0", "source": "https://github.com/acme/sign-in" },
  "inputs": { "email": "anna@example.com", "password": "${secret.password}" },
  "next": "inbox"
}
    • package is the version of the block the test was made with and, when it came from a web address, that address. JEVision fills it in when you add a block from the library. A test without it still works.
    • Inside the block, a step reads a value as ${input.NAME}, such as ${input.email} in the text of a type block.
    • A value the test leaves out gets a warning while you edit, and stops the run with a message that names the missing value, unless the block gives that value a default.
    • The block acts on its own application (the app of its file), uses the same environment as the test, and a failure inside it fails the test. A block can't run itself, directly or through other blocks.

    Making your own block

    Select the blocks on the canvas that belong together and choose Make Block… (right-click, or ⌘K). Give it a name, and JEVision saves them as blocks/NAME.block.json. Wherever the blocks use ${input.NAME}, the new block asks for NAME.

    Changing a block changes every test that uses it. Edit Block in the inspector of a runTest block opens it.

    Sharing a block

    Choose File → Custom Blocks…, find the block under My blocks and click Share…. Fill in who made it, its version and its license, and choose a zip file or a folder.

    • The block id is suggested from your name and the block's name, like com.anna-smith.sign-in. Change it to one you own, such as one starting with a domain name written backwards.
    • For each value the block asks for, you can write a label, shown in the editor instead of the name, and a default, the value a test gets when it leaves that one out.
    • Only the steps of the block and the pictures they use go in the package. Nothing else of your project does.
    • If a step runs a block you installed from someone else, the window shows it as Needs and the package says so too, so the person who installs yours gets the other one as well. See Blocks that use other blocks.
    • The window lists what it left out or what looks wrong, such as a picture that is missing.

    Send the file to a colleague, or publish it on GitHub. Packages are plain files, so you can also write one by hand: see The package format.

    Installing a block

    Choose File → Install Block… (or ⌘K and type “install block”), then do one of these:

    • Choose a block folder or a .zip file with Choose File or Folder….
    • Drop a folder or a .zip file onto the JEVision window, or a link to one.
    • Paste an address: a GitHub repository, a folder in one, a GitHub release or a link to a .zip file. Only https addresses work.

    Nothing is installed at this point. JEVision reads the block and shows what it does; you choose Install after reading. The block goes into the blocks folder of the open project, so tests of this project can run it. Commit that folder and jevision.blocks.json to git, and the whole team has the block.

    If a block with the same id is installed already, the window says which version it is and offers:

    • Update to… when the new version is newer.
    • Go Back to… when it is older.
    • Reinstall when it is the same version.
    • Keep Version… or Cancel to change nothing.

    A block that needs a newer JEVision than yours (its minVersion), has a file that is broken, or asks for a value its steps never use, says so, and a block with an error can't be installed.

    Several blocks from one place

    A folder, a .zip file or an address can hold more than one block, such as a repository with a blocks folder of .jevblock folders, or a release with a .jevblock.zip file for each block. See Publishing on GitHub for the addresses that work.

    The window then lists every block it found, each with a check box, its name, version and author, and what it does. Untick the blocks you don't want and choose Install.

    • When a ticked block needs another block from the same list, that block is installed with it. Blocks are installed in an order that puts the blocks they need first.
    • When a ticked block needs one that is neither installed nor in the list, the window names it. If the block says where to get it, the window offers to fetch it from there; otherwise the block can't be installed until you install the one it needs.
    • Two blocks with the same id in one list are an error, because a project holds one version of an id.

    What you see before you install

    A block can do more than click and type in the app under test. So the window first tells you, step by step and in plain words, what this block does, such as the text it types or the keys it presses. Below it, Needs your attention lists the steps that reach beyond the app under test, each with exactly what it does:

    Shown asStepsWhat you see of the step
    Runs a script on your Macscript, commandThe whole code or command
    Sends requests over the networkhttpThe method, the address and the body
    Reads or changes a databasedatabaseThe file and the query
    Opens apps, files or web pagesopenApp, openFileThe app, the files and the addresses
    Types on the keyboardtype, pressKeysThe text or the keys
    Uses the clipboardclipboardThe text or the variable

    The most worrying kinds come first, and the clipboard is listed more quietly than the rest. Install a block only from people you trust. A script in a block can do anything you can do on your Mac.

    Packages aren't signed: the id and the author are what a package says about itself, not proof of who made it, so judge a block by the place you install it from.

    Installing only copies files. JEVision doesn't run anything from a package until a test that uses the block runs, and then only the steps you were shown.

    Blocks that use other blocks

    A block can run another installed block as one of its steps, so a “Send a message” block can start with the “Sign in” block instead of repeating its steps. It lists the blocks it needs under dependencies in its block.json:

    "dependencies": [
  { "id": "com.acme.sign-in", "version": "^1.2.0", "source": "https://github.com/acme/blocks/tree/main/blocks" }
]
    FieldRequiredValue
    idYesThe id of the block it needs, written like any block id.
    versionNoThe versions that work, as a range. Left out, any version does.
    sourceNoAn https address to install the block from when it is missing.

    A block lists up to 50 others. It can't list itself, or the same block twice.

    Share… lists the installed blocks your block runs here by itself, each with the version you have installed, written as ^ that version, and the address you installed it from. It refuses a block with a step that runs one of your own blocks or a test, because those aren't in the package: make that block a package too, or write the package by hand, as in the example.

    Running the other block

    A step runs the other block with a runTest block. Its test is the path from this block's flow.json to the other block's: installed blocks sit side by side in blocks/, so the path is ../ID.jevblock/flow.json.

    "signIn": {
  "type": "runTest",
  "test": "../com.acme.sign-in.jevblock/flow.json",
  "next": "compose"
}
    • A step may leave the block's folder only this way, and only for a block listed in dependencies. Running a block that isn't listed is an error that names it: “runs ../com.acme.other.jevblock/flow.json, the block com.acme.other, which block.json doesn't list under dependencies; add it there.” Any other path with .. is an error too.
    • A listed block that no step runs is fine.

    Version ranges

    version says which versions of the other block work, the way Cargo and npm write it:

    RangeVersions that fit
    *Any version. The same as leaving version out.
    1.2.3 or =1.2.3Only 1.2.3.
    ^1.2.31.2.3 and newer, before 2.0.0. Before version 1, the next minor version is the limit: ^0.2.3 is 0.2.3 up to 0.3.0, and ^0.0.3 only 0.0.3.
    ~1.2.31.2.3 and newer, before 1.3.0.
    1.x or 1Any 1.something version.
    1.2.x or 1.2Any 1.2.something version.
    >=1.2.0, >1.2.0, <2.0.0, <=1.4.0The same or newer, newer, older, the same or older.
    >=1.2.0 <2.0.0Every part must fit. Separate the parts with spaces or commas.

    A pre-release, such as 2.0.0-beta.1, fits only a range that names a pre-release of the same version, such as >=2.0.0-beta.1. So ^1.2.0 never picks a beta.

    When JEVision checks them

    • Reading a package, before anything is installed, checks that every block the steps run is listed. Whether the listed blocks are there is a question for the project the block goes into.
    • Installing needs every listed block to be installed, or in the same list, in a version that fits. Otherwise the block isn't installed, and the message says what to do, such as “com.acme.messages needs the block com.acme.sign-in ^1.2.0, which isn't installed; install it with `jevision blocks install https://github.com/acme/blocks/tree/main/blocks`.” or “…, but com.acme.sign-in 1.0.0 is installed; install a version that fits.”
    • Blocks that need each other in a circle can't be installed: “the blocks need each other in a circle: com.acme.a → com.acme.b → com.acme.a. Remove one of these dependencies.”
    • A test that runs a block whose dependencies, or theirs in turn, aren't installed in a version that fits gets an error on its runTest block, while you edit and in jevision validate, with the command that installs what is missing.
    • Updating and removing a block that others need asks first: see Updating and removing blocks.

    Updating and removing blocks

    File → Custom Blocks… lists the blocks from the community with their version, author and where they came from.

    • Update appears for a block installed from an address. It fetches the address again and shows what changed before it replaces anything, as an installation does. Blocks installed from a file have no address to update from.
    • When another installed block needs the one you update in a version that the new one isn't, the window says so before anything changes, such as “com.acme.messages needs the block com.acme.sign-in ^1.2.0, and this brings com.acme.sign-in 2.0.0; update com.acme.messages as well, or go ahead knowing it may stop working.” Updating both from one address together is fine.
    • Remove deletes the block. If tests or other installed blocks use it, the window names them and asks first, because they would stop with a message that the block is missing. A block is never removed behind your back.

    Changing an installed block

    An installed block is read-only, because its next update would replace your changes. Open Block in the inspector of a runTest block, and Open beside the block in Custom Blocks…, show it on the canvas to read. A bar above it says so and has the button Make This a Block of the Project…; Make a Copy… in Custom Blocks… does the same. It copies the block into your own blocks, where you can change it:

    • You choose the name of the copy, which starts as the block's name. The copy is blocks/NAME.block.json. Its pictures and files go to blocks/images and blocks/files, under another name when a different file of that name is there already.
    • Steps that run another installed block keep running it.
    • A tick box, on by default, says Use the copy in the tests that use it and names them. If it is on, each of their runTest blocks runs the copy, and a value a test left out gets the default the block gave it, so the tests do what they did before. If it is off, the tests keep using the installed block. A test that is open with changes you haven't saved is left alone, and the window names it.
    • The installed block stays. Remove it in Custom Blocks… once nothing uses it.

    A block whose steps run another file from inside its own package can't be copied, and says so. The pictures a package's checks compare with can't be replaced with Accept as New Reference either: make the block your own first.

    Installing a project's blocks again

    jevision.blocks.json remembers each block installed from an address: the address and the version. Commit it with the tests, and anyone who opens the project, on a new Mac or after a fresh clone, can get the same blocks again.

    • In the app, opening a project with blocks in jevision.blocks.json that aren't installed, or are installed in another version, offers to install them. The offer opens the Install Block window with those blocks in a list: you read what each one does and choose which to install, as for any address.
    • On the command line, jevision blocks restore prints the same plan, and installs it with --yes.

    Each address is fetched once, even when it holds several of the blocks. For each block, JEVision compares what it finds there with jevision.blocks.json:

    What the address hasWhat happens
    The version in jevision.blocks.jsonReady to install.
    Another versionShown as changed, and installed only if you tick it in the app or add --force. The version your team checked must not change without anyone noticing.
    No block with that idShown as missing; nothing to install.
    Nothing: the address can't be reachedShown with the reason; nothing to install from it.

    Blocks are installed the usual way, the blocks they need first, and jevision.blocks.json is updated. A block listed without a version, in a file written before versions were kept, counts as installed in any version.

    Runs and reports

    • The steps of a package are reported under the name and version of the package, such as “in Sign in 1.2.0”, and the report lists the packages a run used with their authors. Statistics and the run list name a package by its id.
    • A test that uses a block that isn't installed is marked while you edit and when you validate, and a run of it stops with “the block is not installed” before anything happens on screen. The error names the block and its version, such as “needs the block com.acme.sign-in 1.2.0”. Install… in the editor and in the report opens the Install Block sheet: it reads the block from the address the test knows, or asks for a file or an address when it doesn't know one. jevision validate and jevision run print the same message with the command to run, such as jevision blocks install https://github.com/acme/sign-in.
    • A block that needs a newer JEVision stops a run with a message that says which version it needs.

    The package format

    A package is a folder named after the id of the block, with .jevblock at the end:

    com.acme.sign-in.jevblock/
  block.json       who made the block, which version it is, what it asks for
  flow.json        the steps: a test like any other
  images/          the pictures the steps use (any folders and names)

    Inside a project it sits in blocks/. Shared as a file, it is that folder, or a .zip file with the folder inside it. Hidden files and links are left out.

    block.json

    {
  "format": 1,
  "id": "com.acme.sign-in",
  "name": "Sign in",
  "description": "Signs in to AcmeMail with an email and a password.",
  "icon": "person.badge.key",
  "version": "1.2.0",
  "author": "Acme QA",
  "license": "MIT",
  "minVersion": "0.1.0",
  "inputs": [
    { "name": "email", "label": "Email address", "default": "qa@example.com" },
    { "name": "password" }
  ],
  "dependencies": [
    { "id": "com.acme.open-app", "version": "^1.0.0", "source": "https://github.com/acme/open-app" }
  ]
}
    FieldRequiredValue
    formatYesAlways 1.
    idYesThree or more parts of lowercase letters, digits and -, joined by dots, such as com.acme.sign-in; up to 100 characters. The installed folder is named after it, and a project can hold one version of an id.
    nameYesWhat the library calls the block; up to 60 characters.
    descriptionNoWhat the block does, in a sentence or two; up to 500 characters.
    iconNoName of an SF Symbol, such as person.badge.key.
    versionYesA semantic version: MAJOR.MINOR.PATCH, optionally followed by -beta.2 and the like. 1.2.0 is newer than 1.2.0-beta.2 and older than 1.10.0.
    authorYesWho made the block; up to 100 characters.
    licenseYesThe name of its license, such as MIT.
    minVersionNoThe oldest JEVision that can run the block. An older JEVision refuses to install or run it.
    inputsNoWhat a test gives the block, up to 50 entries. Each has a name (letters, digits and underscores, not starting with a digit), an optional label to show in the editor instead of the name, and an optional default, the value for a test that leaves it out.
    dependenciesNoThe other blocks its steps run, up to 50 entries, each with an id, an optional version range and an optional source address. See Blocks that use other blocks.

    Unknown fields are errors, so a misspelled name isn't ignored. The same rules are in a JSON Schema that editors can use for completion and checks.

    flow.json

    The steps are a test file as in Test files, with these rules:

    • Every ${input.NAME} the steps read is listed in inputs. An input that no step reads is a warning.
    • Pictures and files are named relative to flow.json and stay inside the package folder: a path with .. is an error. The one way out is a runTest step that runs a block listed in dependencies, as ../ID.jevblock/flow.json: see Running the other block.
    • The app is the application the steps act on. A block rarely has a check; the tests that use it do.

    jevision.blocks.json

    The project keeps where each package came from, and which version was installed, in jevision.blocks.json, in the project folder, so the team can update them and install them again:

    {
  "format": 1,
  "sources": {
    "com.acme.sign-in": "https://github.com/acme/sign-in-block"
  },
  "versions": {
    "com.acme.sign-in": "1.2.0"
  }
}

    JEVision writes both entries when it installs or updates a block from an address, and removes them when the block is removed or installed again from a file or folder: packages installed from a file or folder have no entry. A file without versions, written by an older JEVision, still works.

    An example

    The examples in the repository hold two packages side by side. org.jevision.add-line types a line into TextEdit, and the test add-a-line-with-a-block.flow.json uses it. org.jevision.add-date keeps today's date and runs org.jevision.add-line to type it, so it lists that block under dependencies. Copy the blocks folder anywhere and install it from there: both blocks appear in one list, and org.jevision.add-line is installed first.

    Publishing on GitHub

    People install from a repository or a release by pasting its address into Install Block… or giving it to jevision blocks install:

    AddressWhat is installed
    https://github.com/OWNER/REPO, …/releases, …/releases/latestThe latest release: its file ending in .jevblock.zip if it has one, otherwise the code of the release. A repository with no release gives its main branch.
    https://github.com/OWNER/REPO/releases/tag/TAGThat release, in the same way.
    https://github.com/OWNER/REPO/tree/BRANCHThe code of that branch or tag.
    https://github.com/OWNER/REPO/tree/BRANCH/PATHOnly the folder PATH of that branch or tag, such as …/tree/main/blocks. A branch with / in its name, such as feature/login, works too.
    https://…/NAME.zipThat zip file, on GitHub or anywhere else.

    github.com/OWNER/REPO works too. Packages are found where block.json is. If the top of the repository, folder or zip file is a package, that is the one. Otherwise JEVision looks for package folders up to three levels down, without looking inside a package, and installs all it finds as a list, up to 100. A release with several files ending in .jevblock.zip, up to 20, gives all of them as one list.

    To publish one block: put the .jevblock folder (or its contents) in a repository, and attach com.acme.sign-in.jevblock.zip to each release. To publish several: put them in a blocks folder, one .jevblock folder each, or attach one .jevblock.zip file per block to the release. Blocks that use each other are best published together, with the address of that place as the source of each dependency. Raise version for each release so that Update can tell.

    How packages are kept safe

    • Nothing in a package runs while it is read or installed. Files are copied one by one, without permission to run, and every path is checked first.
    • A zip file can't write outside its own folder: one with a name that has .. in it or starts with / is refused as a whole, and links in it are left out.
    • A download is at most 64 MB, a zip unpacks to at most 256 MB and 20,000 entries, and a package holds at most 1,000 files and 64 MB. A download that takes longer than two minutes stops.
    • For several blocks from one place, the limits on unpacking count all of them together, the files of a release are at most 128 MB together, and a zip file that one of them would refuse refuses the whole list.
    • Addresses must be https, and so must every redirect they lead to.
    • An address that isn't a GitHub repository, release, branch or a link to a .zip file is refused rather than guessed at.

    The command line does the same as the app: see jevision blocks.
