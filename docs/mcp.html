    AI assistants (MCP)

    Let an AI assistant such as Claude, Cursor or Copilot write, fix and run your tests. JEVision speaks the Model Context Protocol (MCP), the common way assistants use outside tools.

    On this page

    • Connect an assistant
    • What assistants may do
    • Tools
    • An example

    Connect an assistant

    1. Install the command-line tool.
    2. Open your project in JEVision and go to Settings → AI → Assistants. Under Connect an Assistant, copy the configuration. It names the project open now: 
      {
  "mcpServers" : {
    "jevision" : {
      "args" : [
        "mcp",
        "--project",
        "/Users/you/Projects/acme-tests"
      ],
      "command" : "/usr/local/bin/jevision"
    }
  }
}
    3. Add it to the MCP servers of your assistant, as its documentation describes. The assistant starts jevision mcp itself when it needs it.

    Without --project, the assistant sees the nearest folder at or above the one it starts jevision in that has a .jevision folder, otherwise that folder itself. See jevision mcp.

    What assistants may do

    An assistant can always find, read, write and check the tests of the project and read its reports. Two things work only after the person at the Mac turns them on in Settings → AI → Assistants, because they act on the Mac or may show private things:

    • Allow assistants to run tests. Tests open apps, click and type on this Mac. Press Esc twice to stop one.
    • Allow assistants to take screenshots. An assistant sees the front window of an app, which may show private information.

    Whatever the settings:

    • Assistants never get the values of secrets or API keys. Tests show secrets only as ${secret.NAME}, and reports mask them.
    • Assistants can't open files outside the project folder.
    • A test with errors is never saved, so an assistant can't break a working test file.

    Tools

    Every path is relative to the project folder, such as login/sign-in.flow.json. Fields marked “required” must be given; the rest are optional.

    list_tests

    Lists the tests in the project with their name, app, tags, status, the rest of their details (such as author, link and the flaky mark) and how many problems each has.

    • query: words to look for in the path, name, description, app or tags. Every word must match; case doesn't matter.
    • folder: only list tests in this folder.

    read_test

    Returns the JSON of a test file exactly as saved, and the problems found in it.

    • path (required): the test file.

    write_test

    Creates or replaces a test file, saved in canonical form. Nothing is saved if the test has errors; the answer lists them with the block and field each concerns.

    • path (required): the test file, ending in .flow.json. Missing folders are created.
    • test (required): the whole test, as a JSON object or its text.

    add_blocks

    Adds blocks to a test as one chain: each leads to the next, and the last one to whatever came after the place they go. Give each block as in a test file, without an id or arrows; ids are made from the block types and returned.

    • path (required): the test file.
    • blocks (required): the blocks in order, such as { "type": "pressKeys", "keys": "cmd+s" }. Only the last one may be an if block.
    • after: the id of the block to add them after; or atStart: true to add them before the first block.
    • edge: which way out of the after block they go: next (default), then, elseIf1, elseIf2… or else for an if block, body to put them inside a repeat or useData block.

    remove_block

    Removes a block and joins its neighbours: whatever led to it then leads to what came after it. Removing a repeat or useData block keeps the blocks inside it; removing an if block keeps its then branch.

    • path (required): the test file.
    • block (required): the id of the block to remove.

    validate_test

    Checks a test file, or every test in a folder, for errors and warnings, each with the block and field it concerns. Tests with errors can't run.

    • path (required): a test file or folder; . for the whole project.

    list_block_types

    Describes the test format: the fields of a test, every block type with its fields and an example, how blocks lead to each other, and the shapes of targets, references, areas and durations. Takes no arguments. Assistants call it before writing a test.

    run_test

    Runs a test, or every test in a folder one after another, on this Mac for real. Needs Allow assistants to run tests and an unlocked screen. Answers at once with a run id; one run at a time.

    • path (required): a test file or folder.
    • retries: run a failed test this many more times, 0 to 10, instead of the number in the test.
    • env: the environment to use, such as staging. Default: the default environment of jevision.environments.json, or none when it names no default.
    • rows: rows of a data-driven test to run: all (default), one row such as 2, or a range such as 2-4.

    get_run

    Tells how a run is going: running or finished, and for each test its verdict (passed, failed, cancelled, notRun, error, running or waiting), the step it is on, why it failed, and the name of its report.

    • run: the run id from run_test. Default: the newest run.
    • wait: seconds to wait for the run to end before answering, 0 to 600. Default: 0, answer at once.

    stop_run

    Stops a run: the running test ends as cancelled and the ones after it don't run.

    • run: the run id. Default: the newest run.

    get_report

    Returns the saved report of one test run: the verdict, every step with its status, why it failed, and what the AI model answered for checks by meaning. Secret values are masked.

    • report: the report name from get_run. Default: the newest report in the project.
    • images: screenshots to include: none (default), failed (those of failed steps) or all, at most 30.

    screenshot

    Returns a picture of the front window of an app, as it is now. Needs Allow assistants to take screenshots. Private parts of the window, such as password fields, are covered with grey boxes.

    • app: the bundle id of the app, such as com.apple.TextEdit; or
    • path: a test file, whose app is pictured.

    An example

    Ask your assistant something like:

    Write a JEVision test that opens TextEdit, makes a new document, types “Hello” and checks the window. Then run it and tell me what failed.

    A typical assistant calls list_block_types to learn the format, write_test to save the test, fixes any errors the answer lists, then run_test, get_run with wait, and get_report with images set to failed to see what went wrong. The first run saves the reference picture of the check, so look at it in JEVision before trusting it. See The first run.
