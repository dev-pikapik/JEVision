    Command line

    The jevision command runs, checks and formats tests from Terminal or a CI system. It also serves tests to AI assistants and starts scheduled runs.

    Install

    The command comes inside the app. Choose JEVision → Install Command Line Tool…. See Getting started. Check that it works:

    jevision --version
jevision --help

    Commands

    CommandWhat it does
    jevision runRun tests on this Mac
    jevision validateCheck tests for errors and warnings
    jevision checkCheck the project carries every file its tests read
    jevision fmtRewrite tests in canonical form
    jevision mcpLet AI assistants read, edit and run tests
    jevision blocksList, install, update, remove and restore blocks that other people shared
    jevision schedule runRun the schedules of a project that are due now
    jevision --help, -h, helpShow help; jevision help run or jevision run --help for one command
    jevision version, --version, -VShow the version; with --json, also the file formats and protocols it supports

    Wherever a command takes tests…, give test files (.flow.json) or folders. Folders are searched for .flow.json files, including folders inside them, in order of their paths. Files and folders whose names start with a dot are skipped.

    Every command ends with an exit status: 0 means all good, 1 means a test failed or a problem was found, and higher numbers say what kept the command from its work.

    Language. Messages, errors, hints and the reports a command writes (--html, --junit, bug drafts) use the language of your Mac, or English when the CI environment variable is set, so logs on a CI machine read the same for everyone. Every command takes --lang code to choose another language of the app, for example jevision run tests/ --lang ru; an unknown code is an error that lists the languages there are. Test files, --json results, issue codes and the names of options never change with the language. New languages are added in the string catalog without changing code (see Contributing).

    Exit codes

    Every command ends with an exit status, a number a script or CI system reads to know how it went. Each number means the same for every command:

    StatusMeaning
    0All good: the tests passed, or no problems were found.
    1A test failed or was stopped, or problems were found in the tests.
    2The command can't be done as asked, and trying again won't help: an unknown command or option, a file or folder that isn't there, a folder with no tests. For jevision issue, also: no run failed, so there is nothing to report, or the project can't take the report as it is, such as one that isn't on GitHub or has no remote.
    3A file couldn't be read or written: a test, a settings file of the project, a report.
    4This Mac isn't ready yet, and trying again later can help: nobody is logged in, the screen is locked, or macOS hasn't allowed jevision what it needs (see below). For jevision issue --send, also: git or the GitHub CLI isn't installed, you aren't signed in to GitHub or your sign-in ran out, your account can't write to the repository, or GitHub can't be reached or turned the report down without saying why. For jevision mcp --pair and --remote, also: the other Mac can't be reached.
    5A file needs a newer JEVision: a test, a block or a settings file saved in a newer format.
    6–63Kept for later versions.

    When several of these happen in one command, the status is the highest of them: a run where a test failed and the JUnit report couldn't be written ends with 3.

    jevision run

    Runs tests on this Mac, one after another or side by side, and saves a report of every run.

    jevision run tests… [options]

    Each of tests is a test file, a folder of tests, or a test's name as the app shows it, without .flow.json: jevision run notes/add-milk.

    OptionWhat it does
    --project folderProject folder. Files the tests use must be inside it, and reports are saved in folder/.jevision/runs. Default: the nearest folder above the tests that has a .jevision folder, otherwise the current folder if it holds the tests.
    --env nameThe environment whose values the tests read as ${env.NAME}, such as staging. Secrets come from the Keychain items of that environment first. Default: the default environment of jevision.environments.json, if any.
    --retries nRun a failed test up to n more times, 0 to 10, instead of the number in the test or the project. See Retries.
    --row nRun a data-driven test with row n of its table only, counting from 1. The header line isn't a row.
    --rows whichRows of a data-driven test to run: all (the default), one row such as 3, or a range such as 2-4. Each row runs the whole test and has its own retries.
    --type type, --priority level, --status status, --author name, --flakyRun only the named tests whose card says so, such as --priority high --type smoke: see Choosing tests by their cards.
    --start-at blockStart from this block instead of the first one. Works with one test only.
    --provider idAI provider for checks by meaning, instead of the one chosen in the app (Settings → AI), unless the project names its own in jevision.project.json or a check names its own, which come first (see --force-ai): anthropic, openai, gemini, jev, ollama, lmstudio or openai-compatible.
    --model nameAI model for checks by meaning, instead of the chosen one. The project's or the check's own choice, if there is one, comes first (see --force-ai).
    --force-aiEvery check by meaning asks this run's provider and model (--provider and --model, otherwise the ones chosen in the app), whatever the project or a check chooses, and never the fallback provider. Made for CI, which has the key of one provider. Before the tests start, one short question to the model checks the API key, the model and the address; when it fails, no test runs and the message says why. Elements a test describes in words are still found by JEV, the only provider that can find them.
    --junit fileAlso save a JUnit XML report of all the tests, for CI.
    --html folderAlso save the HTML report of every run in this folder.
    --video whenRecord a video of the app: off, on-failure (keep it only when the test fails) or always. Default: as chosen in the app (Settings → Advanced), otherwise on-failure.
    --app-copy id=pathTest the copy of an app at path instead of the installed app whose id is id, such as --app-copy com.example.Notes=build/Notes.app. Give it once for each app. See Testing a copy of an app.
    --through-appRun inside the JEVision app instead of the terminal, so only JEVision needs the screen and keyboard permissions. See Running through the app.
    --app pathThe JEVision app to run in with --through-app, when the jevision you run isn't part of one.
    --include-quarantined-failuresCount failures of tests in quarantine like any other failure. Without it they still run, but don't change the exit status and are listed as skipped in the JUnit report. A test whose quarantine until day is past counts either way.
    --parallel [n]Run up to n tests at the same time, 1 to 16, instead of one after another. Without a number: one per core of this Mac; --parallel 1 runs them one after another. Without this option, tests run as the project sets for their folder. Tests that use the screen still take turns. See below. A folder named with digits only needs ./ in front: --parallel 4 ./2024.
    --no-notifyDon't send the message that jevision.notifications.json asks for (Slack, Telegram, email): one message for one test, one summary for several. A stopped run sends nothing. On CI the webhook, bot token and mail password come from JEVISION_SLACK_WEBHOOK, JEVISION_TELEGRAM_TOKEN and JEVISION_SMTP_PASSWORD.
    --jsonPrint the result as JSON (see below). Progress goes to standard error.

    While tests run, JEVision uses the mouse and keyboard. Press Esc twice or Ctrl-C to stop; the stopped test is reported as cancelled. Secrets come from environment variables or the Keychain (see Secrets), and so do API keys of AI providers, such as ANTHROPIC_API_KEY.

    jevision run tests/
jevision run tests/sign-in.flow.json --env staging --retries 2
jevision run tests/ --junit junit.xml --html reports --video always
jevision run tests/ --parallel 4
jevision run tests/ --priority critical --type smoke
    Exit status of jevision run
    StatusMeaning
    0All tests passed. Tests in quarantine may have failed, and tests with no check may have finished without checking anything: the output says so and the JUnit report lists them as skipped.
    1A test failed or was stopped.
    2Wrong arguments: a file or folder that isn't there, an environment the project doesn't have, or no test fits the filter.
    3A file couldn't be read or written: the environments file, the JUnit or HTML report, or the report of a test.
    4This Mac can't run tests now (see below).
    5A test, a block it uses or the environments file needs a newer JEVision.

    Choosing tests by their cards

    The card of a test is its testType, priority, status and author (see Fields of a test) and whether it is flaky. Add one or more options to jevision run to run only the tests among tests that fit:

    • --type: smoke, regression or acceptance.
    • --priority: critical, high, medium or low.
    • --status: draft, ready or outdated.
    • --author: the name written in the test; case and spaces around it don't matter.
    • --flaky: tests marked flaky in their card, and tests whose runs saved in the project found them flaky over the last 30 days, as the app does.

    The options combine: a test must fit all of them. A test whose card doesn't say a field you ask for isn't run. The output says how many tests the filter left out. When none fits, nothing runs and the exit status is 2. The sidebar of the app filters in the same way, and Run All then runs only the tests you see.

    jevision run tests/ --priority critical --type smoke
jevision run tests/ --flaky --retries 3
jevision run tests/ --author "Anna Lee" --status ready

    Running tests side by side

    Tests run one after another unless the project or --parallel says otherwise. --parallel 4 runs up to four tests at a time, --parallel alone runs one per core of the Mac (at most 16), and --parallel 1 runs them one after another. Side by side, a suite of tests that don't need the screen finishes sooner.

    Without --parallel, the tests run the way the project sets for their folder. In the app, right-click a folder and choose under Run Tests, or right-click All Tests for the whole project. The choice is kept in jevision.project.json, so the app, jevision run and CI run the tests the same way.

    • Which folder. The folder you name; for several tests or folders, the deepest folder that holds them all. A folder with no choice of its own takes the one of the folder above it, up to the whole project.
    • Nothing set. When no folder up to the project has a choice, the tests run one after another. When jevision.project.json can't be read, they run one after another too, and the run says why.
    • The run says so. When the tests run side by side because of the project, the line after the first one tells where the choice comes from:
    Running 6 tests in /Users/ann/Notes, up to 4 at a time. Press Esc twice or Ctrl-C to stop.
Side by side, as jevision.project.json sets for the folder “login”. Add --parallel 1 to run them one at a time.
    • The screen is never shared. A test that clicks, types, looks at the screen, runs AppleScript or uses the clipboard has the screen to itself: another test that does the same waits. Only tests that leave the screen alone run beside it: commands, requests, files, databases, scripts other than AppleScript, pauses, dates, loops and conditions on values. A test that runs another test counts as the tests it runs, and a test JEVision can't read counts as one that uses the screen. If every test uses the screen, --parallel changes nothing.
    • “Runs after” is kept. A test starts only after the tests it runs after (dependsOn in the test) have passed. When one of them fails, the tests that need it are blocked, as without --parallel.
    • The output stays readable. The lines of a test are printed together when it ends, so the test that ends first is printed first. The JUnit report, the HTML reports and the --json result keep the order of the tests, the same as without --parallel.
    • Stopping. Esc twice or Ctrl-C stops every test that is running, and each is reported as cancelled. The tests that hadn't started are reported as not run. The exit status is the same as without --parallel.
    • It works with --env, data-driven tests (the rows of a test still run one after another), --retries, --junit, --html and --json.

    The app, other jevision commands and AI assistants on the same Mac take turns with this run: a test that uses the screen waits while another run has it. See One run at a time on the screen.

    One run at a time on the screen

    Only one run can move the mouse and type on a Mac at a time. The JEVision app, jevision run and the assistants of jevision mcp share one lock for it, kept in ~/Library/Application Support/JEVision/screen.lock. A test that clicks, types, looks at the screen, runs AppleScript or uses the clipboard takes the lock when it starts and gives it back when it ends. A test that doesn't use the screen never takes it.

    A program that only tests JEVision, with no screen to drive, can keep out of this by setting JEVISION_SCREEN_LOCK to the path of a lock file of its own: its runs then neither wait for the runs above nor make them wait.

    When another run has it, the test waits and says who has it, then starts as soon as the screen is free:

      Screen busy: JEVision, test Sign in, since 12:03. Waiting for it.

    Nothing needs cleaning up: if the run that has the screen crashes or is stopped, the Mac frees the lock by itself. Esc twice or Ctrl-C stops a run that waits, and it is reported as cancelled.

    Testing a copy of an app

    Tests name the app they use by its id, such as com.example.Notes, so they normally open the app installed under that id. To test another copy of it, for example the one you just built, name the copy with --app-copy:

    jevision run tests/ --app-copy com.example.Notes=build/Notes.app
    • Only the copy is used. Wherever a test names com.example.Notes, the run opens, looks at, records and quits the app at build/Notes.app. The installed app can stay open: the copy starts on its own next to it, and the test never touches the installed one.
    • The path is a folder ending in .app, absolute or from the current folder.
    • Several apps: give --app-copy once for each, such as --app-copy com.example.Notes=Notes.app --app-copy com.example.Sync=Sync.app. Apps that aren't named are the installed ones, as always.

    Running through the app

    macOS asks for the Screen & System Audio Recording and Accessibility permissions for the app that jevision runs in: Terminal, your editor or your CI agent, each one separately. With --through-app, the JEVision app runs the tests instead, so allowing JEVision once is enough wherever you start the run from:

    jevision run tests/ --through-app

    It works the same as without it: what the run prints shows in your terminal, Ctrl-C stops the run, and the exit status is the run's own. The app runs in the background with no window and no Dock icon, gets your current folder and environment variables, and quits when the run ends. If the app can't be found or opened, or quits before the run ends, the exit status is 2 and the message says why.

    The app it uses is the first one found of:

    1. the JEVision app the jevision you run comes from, when it was installed with JEVision → Install Command Line Tool…;
    2. the app named with --app path;
    3. the app named by the JEVISION_APP environment variable;
    4. /Applications/JEVision.app, then ~/Applications/JEVision.app.

    The result of run --json

    With --json, standard output holds only this result, so a script can read it:

    {
  "jsonVersion": 1,
  "passed": 1,
  "nothingChecked": 0,
  "failed": 1,
  "quarantined": 0,
  "cancelled": 0,
  "blocked": 0,
  "notRun": 0,
  "errors": 0,
  "tests": [
    {
      "file": "sign-in.flow.json",
      "verdict": "failed",
      "name": "Sign in",
      "flaky": false,
      "quarantined": false,
      "quarantineReason": null,
      "blockedBy": null,
      "addedAsDependency": false,
      "attempts": 3,
      "rows": [],
      "durationMs": 18234,
      "newReferences": [],
      "failure": { "code": "…", "message": "…", "params": { … } },
      "report": "…/.jevision/runs/20261018-031500-sign-in/report.json",
      "html": null,
      "video": null
    }
  ]
}
    • verdict is passed, nothingChecked (finished, but no block looked at the screen, so the test couldn't have caught a wrong result), failed, quarantined (failed, but in quarantine), cancelled, blocked (didn't run because a test it depends on didn't pass; blockedBy says which and why), notRun (the run was stopped before this test) or error (the run couldn't save its report; error then holds the reason).
    • blockedBy of a blocked test is an object: reason is failed (the test behind it ran and failed), notRun (it couldn't run), missing (it isn't there) or cycle (tests depend on each other in a circle, and cycle lists them round it); dependency is the test's own dependency and cause the test that didn't pass, which can be further down the chain; message says it in words, such as Blocked: Login failed. For other tests it is null.
    • failure has a code, such as run.target.notFound, a message, and params: the details the message names, such as the block or the value, as text by name, so a script doesn't have to pick them out of the message.
    • addedAsDependency is true for a test you didn't choose that ran because a chosen test depends on it.
    • file is relative to the project folder. newReferences lists the reference images this run saved for the first time.
    • For a data-driven test, rows holds one entry per row: row, label, verdict, flaky, attempts and failure, with a code, a message and params as above.

    Every --json result is an object that starts with jsonVersion, now 1. Within a version, members are only added, never renamed or removed, so a script keeps working when JEVision is updated. Codes such as verdict, reason and code stay the same in every language; message next to a code says the same in words, in the language of the messages.

    When validate, check or run can't do all its work, the JSON result says why in error, with a code and a message, and standard error says it too. The result has what the command got done as well: tests of validate lists the files it could read, and a run whose report couldn't be saved still has its tests. When several things went wrong, error tells the one that set the exit status, and standard error tells each of them.

    {
  "jsonVersion": 1,
  "error": {
    "code": "noTests",
    "message": "there are no tests (*.flow.json files) in /Users/ann/Shop"
  }
}
    codeWhat went wrongExit status
    usageAn unknown command or option, or an option without its value2
    noFileOrFolder, noFolderA file or folder named isn't there2
    noTestsA folder or project has no tests2
    noTestFitsThe filter leaves no test to run2
    outsideProjectA test isn't in the project given with --project2
    noEnvironment, noEnvironmentsFileThe project has no environment by the name given, or no environments at all2
    modelNeedsProvider--model without a provider to ask2
    cannotReadA test or folder couldn't be read; one that isn't there ends with 23
    environmentsUnreadableThe environments file of the project couldn't be read3, or 5 when a newer JEVision saved it
    cannotWriteThe JUnit or HTML report couldn't be saved3
    notReady, noKeyboardWatchThis Mac isn't ready to run tests (see below), or Esc twice couldn't be set up to stop the run4

    jevision validate

    Checks test files for errors and warnings, as the editor does. See Problems the editor reports.

    jevision validate tests… [--json]
    OptionWhat it does
    --jsonPrint the result as JSON: jsonVersion and tests, a list with one entry per file, with file, valid and issues. Each issue has a code such as flow.edge.unknownTarget, a severity (error or warning), params with the details and a message. A file or folder that can't be read, or a folder with no tests, is in error. See versions of the JSON result.

    Exit status: 0, all good; 1, problems found; 2, wrong arguments, a file or folder that isn't there, or a folder with no tests; 3, a file couldn't be read; 5, a test needs a newer JEVision.

    jevision check

    Checks that a project carries every file its tests read, so it runs the same once copied, cloned or on CI. A test can pass on your Mac and fail everywhere else when it reads a file that only your Mac has.

    jevision check [project] [--json]

    Without project, it checks the project the current folder is in. Every test of the project and every block of your own (.flow.json and .block.json files, except in folders whose names start with a dot) is checked, and in each of them every path to a file or folder: the files a test opens, the pictures it clicks, drags, scrolls, types into, waits for or puts on the clipboard (and their dark versions), the CSV tables it reads data from, the tests it runs, the references of its checks, the folders its commands run in, the tests it runs after, and the files attached to its notes. A note doesn't change how the test runs, so problems with its files are only warnings.

    FoundWhy it mattersIs
    A path to a place on this computer only, such as /Users/ann/button.png, ~/button.png or C:\button.pngNo other computer has itError
    A path out of the project folder, such as ../../button.png, or through a link that leads out of itThe file isn't copied, cloned or committed with the projectError
    \ between foldersOnly Windows reads it; JEVision paths use /Error
    A name that differs from the file on disk in capital letters, such as data/users.csv for Data/users.csvThe Mac finds it; Linux, most CI runners and some Mac disks don'tError
    A file or folder that isn't thereThe test fails when it gets thereError
    A file of 50 MB or moreGitHub refuses files over 100 MB and warns from 50 MB; keep such files in Git LFSWarning
    A reference of a check block that isn't saved yetThe first run saves itWarning

    A path with placeholders, such as ${var.folder}/logo.png, names a file only while the test runs, so only its part before the first placeholder is checked: /tmp/${var.name}.png is still a path on this computer only, and ../../${var.name}.png still leads out of the project. The files of “check a file” and database blocks aren't checked: they belong to the app under test, not to the project.

    jevision validate shows the same problems of a test in a project as warnings, so a test you are still writing isn't stopped by them; jevision check counts them as errors.

    OptionWhat it does
    --jsonPrint the result as JSON: jsonVersion and tests, a list with one entry per test, with file, valid and issues, as validate --json does. Issue codes start with check., such as check.path.case. A folder that isn't there, or a project with no tests, is in error instead.
     
    $ jevision check
login/sign-in.flow.json: 1 error, 0 warnings
  error   Block “avatar”, field “target.image”: “/Users/ann/avatar.png” points to a place on this computer only, so the test won’t find the file anywhere else. Put the file in the project and choose it again.
1 test checked: 1 error, 0 warnings

    Exit status: 0, all good; 1, errors found; 2, wrong arguments, a folder that isn't there, or a project with no tests (so a check of the wrong folder doesn't pass without checking anything); 3, a file or folder couldn't be read; 5, a test needs a newer JEVision.

    jevision fmt

    Rewrites test files in canonical form, so every change shows up as a small, readable diff.

    jevision fmt tests… [--check]
    OptionWhat it does
    --checkOnly list the files that are not in canonical form, and change nothing. Useful in CI.

    Exit status: 0, all good; 1, a file is not in canonical form or can't be read as a test; 2, wrong arguments, a file or folder that isn't there, or a folder with no tests; 3, a file couldn't be read or written; 5, a test needs a newer JEVision.

    jevision mcp

    Serves the tests of a project to AI assistants on this Mac, such as Claude, Cursor or Copilot, over the Model Context Protocol. The assistant starts this command itself; you add it to the assistant's settings. See AI assistants (MCP).

    An assistant that runs tests through it is asked about first on the Mac, and the app lists the assistants that connected: see Asking first.

    With --remote it serves the assistant from another Mac instead: see From another Mac.

    jevision mcp [--project folder]
jevision mcp --pair link
jevision mcp --remote Mac [--project name]
jevision mcp --forget Mac
    OptionWhat it does
    --project folderProject folder whose tests the assistant may see. Default: the nearest folder at or above the current one that has a .jevision folder, otherwise the current folder. With --remote, the name of the project open in JEVision on that Mac; default: that project, whatever its name.
    --pair linkPairs this computer with a Mac, using the one-time command that Settings → iPhone & Remote → Add → Assistant on another computer shows on that Mac. The code works once, for five minutes.
    --remote MacServes the assistant with the tests of a paired Mac, by its name or the start of its id. The assistant starts this command itself.
    --forget MacRemoves a paired Mac from this computer. To also cut this computer off on the Mac, choose Disconnect there.

    Exit status: 0, the assistant disconnected, or the Mac was paired or forgotten; 2, wrong arguments, no project, or a Mac that isn't paired; 3, the list of paired Macs, this computer's key, or the assistant's input or output couldn't be read or written; 4, the other Mac can't be reached, or this computer has no key.

    jevision blocks

    Lists, installs, updates and removes the blocks that other people shared in a project, as Install Block… and Custom Blocks… do in the app, and installs the blocks of a project again from jevision.blocks.json. Installed blocks are in the blocks folder of the project.

    jevision blocks list [--project folder]
jevision blocks install source [--only id,…] [--yes] [--force] [--project folder]
jevision blocks update [id] [--yes] [--force] [--project folder]
jevision blocks remove id [--force] [--project folder]
jevision blocks restore [--only id,…] [--yes] [--force] [--project folder]
    CommandWhat it does
    listPrint the installed blocks: id, version and name, where each comes from (a GitHub account, a site or Source unknown), the author it names, and the address it was installed from.
    install sourceRead a block and print what it does. source is a block folder, a .zip file, or an https address of a GitHub repository, a folder in one, a GitHub release or a .zip file. A source can hold several blocks; then all of them are read and installed. Nothing is installed without --yes.
    update [id]Fetch the address a block was installed from again, and print what changed. Without an id, every block that has an address. Installs the new version with --yes.
    remove idRemove a block. A block that tests or other installed blocks use is not removed unless you add --force; the message names them.
    restoreInstall the blocks that jevision.blocks.json lists and the project doesn't have, or has in another version: see Installing a project's blocks again. Prints the plan; installs it with --yes.
    OptionWhat it does
    --project folderThe project to work in. Default: the nearest folder at or above the current one that has a .jevision folder, otherwise the current folder.
    --only id,…With install and restore: work on these blocks only, with the blocks they need. Ids are separated by commas; an id the source or the list doesn't have is an error.
    --yesInstall after printing what the blocks do. For people who have read it, and for scripts.
    --forceInstall the same version again, or an older one over a newer one; install a new version of a block that another installed block needs in another version; with restore, install a block whose version at its address isn't the one in jevision.blocks.json; or remove a block that tests or other blocks use.

    Without --yes, install prints the block's name, version and license, where it comes from and the author it names, with a warning when that isn't the GitHub account or site it comes from, then What it does: with a numbered line for each step. Steps that run a script, send a request, read a database, open apps or files, type on the keyboard or use the clipboard are repeated under Needs your attention:, grouped by kind and with exactly what they do, such as the whole script. It ends with Not installed: add --yes to install it. and the exit status 1.

    A source with several blocks prints each of them this way, in the order they would be installed: the blocks that others need come first. A block that needs one that is neither installed in a version that fits nor in the source stops the installation, with the command that installs it:

    Package: com.acme.messages needs the block com.acme.sign-in ^1.2.0, which isn't installed; install it with `jevision blocks install https://github.com/acme/blocks/tree/main/blocks`.

    Without --yes, restore prints, for each block to install again, what it found at the address (ready, another version, missing there, or the address can't be reached), and for the blocks it would install, What it does: as install does. It installs nothing, ends with Not installed: add --yes to install it. and the exit status 1. With --yes it installs the blocks that are ready, the blocks they need first; a block in another version also needs --force. When the project has everything already, it prints Everything in jevision.blocks.json is installed already. with the exit status 0.

    jevision blocks install https://github.com/acme/sign-in-block
jevision blocks install https://github.com/acme/sign-in-block --yes
jevision blocks list
jevision blocks install https://github.com/acme/blocks/tree/main/blocks
jevision blocks update --yes
jevision blocks remove com.acme.sign-in
jevision blocks restore --yes

    A test that needs a block you haven't installed says so in jevision validate and jevision run, with the id and version the test was made with and the command that installs it, such as needs the block com.acme.sign-in 1.2.0 … install it with `jevision blocks install https://github.com/acme/sign-in-block`. A test that knows no address says jevision blocks install <folder, .zip file or https address>.

    Exit status: 0, done (or nothing to do); 1, a block wasn't installed because --yes is missing, --force is needed (to go back to an older version, to update a block that another one needs in another version, or to restore a block whose version changed), a block it needs is missing, or the block has an error; a block that is installed already in the same version is left as it is, with status 0; 2, wrong arguments, a project folder that isn't there, a block that isn't installed, or a source that isn't a block folder, a .zip file or an https address; 3, a source that can't be read or downloaded; 5, the block needs a newer JEVision.

    jevision schedule run

    Runs the schedules of a project that are due now. The app sets up macOS to start this command at the right times, so you don't need to run it yourself.

    jevision schedule run project

    A schedule is due once for its latest time since the last check, even when the Mac slept through it, unless that time is more than 12 hours ago. When the screen is locked, nobody is logged in, or macOS hasn't allowed jevision to record the screen and control the computer, the run is skipped and nothing is clicked or typed.

    Exit status: 0, nothing was due or all tests passed; 1, a test failed; 2, the project folder isn't there, or a run asked for something the project doesn't have; 3, the schedule file or the history of runs couldn't be read or written; 4, a run was skipped because this Mac wasn't ready; 5, the schedule file, the history of runs or a test needs a newer JEVision.

    jevision version

    Shows the version, as jevision --version does. With --json, it also tells which file formats and protocols this version reads and speaks, so a script can check it works with your files before it runs anything.

    jevision version [--json]
    $ jevision version --json
{
  "jsonVersion": 1,
  "version": "0.1.0",
  "formats": [
    { "file": "*.flow.json", "version": 1 },
    { "file": "*.block.json", "version": 1 },
    { "file": "jevision.project.json", "version": 1 },
    { "file": "jevision.environments.json", "version": 1 },
    { "file": "jevision.schedule.json", "version": 1 },
    { "file": "block.json", "version": 1 },
    { "file": "report.json", "version": 1 }
  ],
  "iphoneProtocol": { "oldest": 1, "newest": 1 },
  "mcpProtocols": ["2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05"]
}
    • formats lists the files by name, or by the ending of their name: tests, your own blocks, the settings of a project, its environments and schedules, the description of a shared block (block.json) and the report of a run. version is the format this version writes in the file; a file with a higher one needs a newer JEVision, and commands that meet one end with status 5.
    • iphoneProtocol is the range of versions of the connection between the iPhone app and this Mac. The iPhone app works with this Mac when its version is in the range.
    • mcpProtocols are the versions of the Model Context Protocol jevision mcp speaks, newest first.

    What a Mac needs to run tests

    Before running anything, jevision run checks that the Mac can run tests, and if not, says what to do and exits with status 4. A Mac can run tests when:

    • a user is logged in and jevision runs in that user's session: from Terminal, from a CI agent started in that session, or over SSH as that same user while they stay logged in at the screen, as in a virtual machine; not as a system service;
    • the screen is unlocked;
    • the app jevision runs in (Terminal, your editor or your CI agent) is allowed under Screen & System Audio Recording and Accessibility. The message names that app and the lists to turn it on in. See Permissions. With --through-app that app is JEVision itself.

    Running in CI

    Tests need a real screen with a logged-in user, so cloud-hosted CI runners can't run them. Use a Mac of your own as a runner. For GitHub Actions, set up a self-hosted runner and install it as a service with ./svc.sh install while logged in as the user who runs the tests. On macOS this makes a launch agent that runs in that user's session. Then allow Screen Recording and Accessibility for the program the first run names.

    jobs:
  ui-tests:
    runs-on: [self-hosted, macOS]
    steps:
      - uses: actions/checkout@v4
      - name: Check test files
        run: jevision validate tests && jevision fmt --check tests && jevision check tests
      - name: Restore the last result of each test
        uses: actions/cache/restore@v4
        with:
          path: |
            tests/.jevision/last-results.json
          key: jevision-last-results-${{ github.run_id }}-${{ github.run_attempt }}
          restore-keys: jevision-last-results-
      - name: Run UI tests
        env:
          ACME_PASSWORD: ${{ secrets.ACME_PASSWORD }}
        run: jevision run tests --junit junit.xml --html reports
      - name: Save the last result of each test
        if: always()
        uses: actions/cache/save@v4
        with:
          path: |
            tests/.jevision/last-results.json
          key: jevision-last-results-${{ github.run_id }}-${{ github.run_attempt }}
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: jevision-reports
          include-hidden-files: true
          overwrite: true
          path: |
            junit.xml
            reports/
            tests/.jevision/runs/

    Secrets go in as environment variables named like the secret, here ACME_PASSWORD for ${secret.ACME_PASSWORD}.

    The cache keeps the last result of each test from one job to the next, so notifications can tell a new failure from one that goes on. jevision check fails the job before the tests run when a test reads a file the repository doesn't have.

    Checks by meaning in CI. The project, or a check, may choose an AI whose key the CI machine doesn't have. --force-ai makes every check by meaning in the run ask the provider and model you give, so the run needs that one key only:

          - name: Run UI tests
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        run: jevision run tests --provider openai --model gpt-5-mini --force-ai --junit junit.xml --html reports

    The log then starts with the line Every check by meaning asks OpenAI, model gpt-5-mini (--force-ai). A missing key, a model the provider doesn't have or a server out of reach stops the command with exit status 2 before any test runs. Tests that find elements by their description also need TYPESAFE_API_KEY for JEV.

    The app can write the workflow for you: Settings → Advanced → Continuous Integration → Add to Project…. It shows the file first, with the secrets your tests use, and saves it as .github/workflows/jevision.yml at the top of the git repository your project is in. It replaces an existing file only after you confirm, and it doesn't commit or push anything.

    CI runs in the app

    The artifact jevision-reports also carries the run reports, with their screenshots, from .jevision/runs. In a CI job, jevision run writes where the run came from into each report: the CI system, the repository, the branch, the commit, the pull request and the page of the run. GitHub Actions, GitLab CI, Buildkite, CircleCI and Jenkins are recognized.

    When you are signed in to GitHub (Settings → Git and GitHub) and the project's repository is on GitHub, the app fetches the artifacts of the newest runs each time you open Runs, and when you click the refresh button above the list. It adds the runs to the project's history, each artifact once, even if you fetch again or delete a run. They are marked CI · pull request #482 or CI · branch main, and the report links to the run on GitHub. The filter above the list (This Mac, Schedule, iPhone, CI) shows only the runs started that way. Without a sign-in nothing is fetched, and the CI filter says how to sign in. The sign-in is kept in the Keychain and is never written to the project or to a log.

    An artifact is at most 512 MB, and the app looks at the 20 newest. Artifacts of an older workflow, which was named ui-test-reports and had no run reports, aren't read: add the workflow to the project again.

    To be told in Slack, Telegram or email when the run fails, set up Notifications in the app and commit jevision.notifications.json; jevision run sends one summary when it finishes, and on CI reads the secrets from environment variables.
