    Command line

    The jevision command runs, checks and formats tests from Terminal or a CI system. It also serves tests to AI assistants and starts scheduled runs.

    Install

    The command comes inside the app. Choose JEVision → Install Command Line Tool…. See Getting started. Check that it works:

    jevision --version
jevision --help

    Commands

    CommandWhat it does
    jevision runRun tests on this Mac
    jevision validateCheck tests for errors and warnings
    jevision fmtRewrite tests in canonical form
    jevision mcpLet AI assistants read, edit and run tests
    jevision blocksList, install, update, remove and restore blocks that other people shared
    jevision schedule runRun the schedules of a project that are due now
    jevision --help, -h, helpShow help; jevision help run or jevision run --help for one command
    jevision --version, -VShow the version

    Wherever a command takes tests…, give test files (.flow.json) or folders. Folders are searched for .flow.json files, including folders inside them, in order of their paths. Files and folders whose names start with a dot are skipped.

    Every command ends with an exit status, a number a script or CI system reads to know how it went: 0 means all good, 1 means a test failed or a problem was found, and 2 means the command itself couldn't do its work.

    jevision run

    Runs tests on this Mac, one after another (or side by side), and saves a report of every run.

    jevision run tests… [options]

    Each of tests is a test file, a folder of tests, or a test's name as the app shows it, without .flow.json: jevision run notes/add-milk.

    OptionWhat it does
    --project folderProject folder. Files the tests use must be inside it, and reports are saved in folder/.jevision/runs. Default: the nearest folder above the tests that has a .jevision folder, otherwise the current folder if it holds the tests.
    --env nameThe environment whose values the tests read as ${env.NAME}, such as staging. Secrets come from the Keychain items of that environment first. Default: the default environment of jevision.environments.json, if any.
    --retries nRun a failed test up to n more times, 0 to 10, instead of the number in the test or the project. See Retries.
    --row nRun a data-driven test with row n of its table only, counting from 1. The header line isn't a row.
    --rows whichRows of a data-driven test to run: all (the default), one row such as 3, or a range such as 2-4. Each row runs the whole test and has its own retries.
    --type type, --priority level, --status status, --author name, --flakyRun only the named tests whose card says so, such as --priority high --type smoke: see Choosing tests by their cards.
    --start-at blockStart from this block instead of the first one. Works with one test only.
    --provider idAI provider for checks by meaning, instead of the one chosen in the app (Settings → AI), unless the project names its own in jevision.project.json, which comes first: anthropic, openai, gemini, jev, ollama, lmstudio or openai-compatible.
    --model nameAI model for checks by meaning, instead of the chosen one. The project's own choice, if it has one, comes first.
    --junit fileAlso save a JUnit XML report of all the tests, for CI.
    --html folderAlso save the HTML report of every run in this folder.
    --video whenRecord a video of the app: off, on-failure (keep it only when the test fails) or always. Default: as chosen in the app (Settings → Advanced), otherwise on-failure.
    --include-quarantined-failuresCount failures of tests in quarantine like any other failure. Without it they still run, but don't change the exit status and are listed as skipped in the JUnit report. A test whose quarantine until day is past counts either way.
    --parallel [n]Run up to n tests at the same time, 1 to 16, instead of one after another. Without a number: one per core of this Mac. Tests that use the screen still take turns. See below. A folder named with digits only needs ./ in front: --parallel 4 ./2024.
    --no-notifyDon't send the message that jevision.notifications.json asks for (Slack, Telegram, email): one message for one test, one summary for several. A stopped run sends nothing. On CI the webhook, bot token and mail password come from JEVISION_SLACK_WEBHOOK, JEVISION_TELEGRAM_TOKEN and JEVISION_SMTP_PASSWORD.
    --jsonPrint the result as JSON (see below). Progress goes to standard error.

    While tests run, JEVision uses the mouse and keyboard. Press Esc twice or Ctrl-C to stop; the stopped test is reported as cancelled. Secrets come from environment variables or the Keychain (see Secrets), and so do API keys of AI providers, such as ANTHROPIC_API_KEY.

    jevision run tests/
jevision run tests/sign-in.flow.json --env staging --retries 2
jevision run tests/ --junit junit.xml --html reports --video always
jevision run tests/ --parallel 4
jevision run tests/ --priority critical --type smoke
    Exit status of jevision run
    StatusMeaning
    0All tests passed. Tests in quarantine may have failed, and tests with no check may have finished without checking anything: the output says so and the JUnit report lists them as skipped.
    1A test failed or was stopped.
    2Wrong arguments, a file could not be read or written, or this Mac can't run tests now (see below).

    Choosing tests by their cards

    The card of a test is its testType, priority, status and author (see Fields of a test) and whether it is flaky. Add one or more options to jevision run to run only the tests among tests that fit:

    • --type: smoke, regression or acceptance.
    • --priority: critical, high, medium or low.
    • --status: draft, ready or outdated.
    • --author: the name written in the test; case and spaces around it don't matter.
    • --flaky: tests marked flaky in their card, and tests whose runs saved in the project found them flaky over the last 30 days, as the app does.

    The options combine: a test must fit all of them. A test whose card doesn't say a field you ask for isn't run. The output says how many tests the filter left out. When none fits, nothing runs and the exit status is 2. The sidebar of the app filters in the same way, and Run All then runs only the tests you see.

    jevision run tests/ --priority critical --type smoke
jevision run tests/ --flaky --retries 3
jevision run tests/ --author "Anna Lee" --status ready

    Running tests side by side

    Tests run one after another unless you add --parallel. --parallel 4 runs up to four tests at a time, and --parallel alone runs one per core of the Mac (at most 16), so a suite of tests that don't need the screen finishes sooner.

    • The screen is never shared. A test that clicks, types, looks at the screen, runs AppleScript or uses the clipboard has the screen to itself: another test that does the same waits. Only tests that leave the screen alone run beside it: commands, requests, files, databases, scripts other than AppleScript, pauses, dates, loops and conditions on values. A test that runs another test counts as the tests it runs, and a test JEVision can't read counts as one that uses the screen. If every test uses the screen, --parallel changes nothing.
    • “Runs after” is kept. A test starts only after the tests it runs after (dependsOn in the test) have passed. When one of them fails, the tests that need it are blocked, as without --parallel.
    • The output stays readable. The lines of a test are printed together when it ends, so the test that ends first is printed first. The JUnit report, the HTML reports and the --json result keep the order of the tests, the same as without --parallel.
    • Stopping. Esc twice or Ctrl-C stops every test that is running, and each is reported as cancelled. The tests that hadn't started are reported as not run. The exit status is the same as without --parallel.
    • It works with --env, data-driven tests (the rows of a test still run one after another), --retries, --junit, --html and --json.

    The app, other jevision commands and AI assistants on the same Mac take turns with this run: a test that uses the screen waits while another run has it. See One run at a time on the screen.

    One run at a time on the screen

    Only one run can move the mouse and type on a Mac at a time. The JEVision app, jevision run and the assistants of jevision mcp share one lock for it, kept in ~/Library/Application Support/JEVision/screen.lock. A test that clicks, types, looks at the screen, runs AppleScript or uses the clipboard takes the lock when it starts and gives it back when it ends. A test that doesn't use the screen never takes it.

    When another run has it, the test waits and says who has it, then starts as soon as the screen is free:

      Screen busy: JEVision, test Sign in, since 12:03. Waiting for it.

    Nothing needs cleaning up: if the run that has the screen crashes or is stopped, the Mac frees the lock by itself. Esc twice or Ctrl-C stops a run that waits, and it is reported as cancelled.

    The result of run --json

    With --json, standard output holds only this result, so a script can read it:

    {
  "passed": 1,
  "nothingChecked": 0,
  "failed": 1,
  "quarantined": 0,
  "cancelled": 0,
  "blocked": 0,
  "notRun": 0,
  "errors": 0,
  "tests": [
    {
      "file": "sign-in.flow.json",
      "verdict": "failed",
      "name": "Sign in",
      "flaky": false,
      "quarantined": false,
      "quarantineReason": null,
      "blockedBy": null,
      "addedAsDependency": false,
      "attempts": 3,
      "rows": [],
      "durationMs": 18234,
      "newReferences": [],
      "failure": { "code": "…", "message": "…" },
      "report": "…/.jevision/runs/20261018-031500-sign-in/report.json",
      "html": null,
      "video": null
    }
  ]
}
    • verdict is passed, nothingChecked (finished, but no block looked at the screen, so the test couldn't have caught a wrong result), failed, quarantined (failed, but in quarantine), cancelled, blocked (didn't run because a test it depends on didn't pass; blockedBy says which and why), notRun (the run was stopped before this test) or error (the run couldn't save its report; error then holds the reason).
    • addedAsDependency is true for a test you didn't choose that ran because a chosen test depends on it.
    • file is relative to the project folder. newReferences lists the reference images this run saved for the first time.
    • For a data-driven test, rows holds one entry per row: row, label, verdict, flaky, attempts and failure.

    jevision validate

    Checks test files for errors and warnings, as the editor does. See Problems the editor reports.

    jevision validate tests… [--json]
    OptionWhat it does
    --jsonPrint the result as JSON: a list with one entry per file, with file, valid and issues. Each issue has a code such as flow.edge.unknownTarget, a severity (error or warning) and params with the details.

    Exit status: 0, all good; 1, problems found; 2, wrong arguments, a folder with no tests, or a file that could not be read.

    jevision fmt

    Rewrites test files in canonical form, so every change shows up as a small, readable diff.

    jevision fmt tests… [--check]
    OptionWhat it does
    --checkOnly list the files that are not in canonical form, and change nothing. Useful in CI.

    Exit status: 0, all good; 1, a file is not in canonical form or can't be read as a test; 2, wrong arguments, a folder with no tests, or a file that could not be read or written.

    jevision mcp

    Serves the tests of a project to AI assistants on this Mac, such as Claude, Cursor or Copilot, over the Model Context Protocol. The assistant starts this command itself; you add it to the assistant's settings. See AI assistants (MCP).

    An assistant that runs tests through it is asked about first on the Mac, and the app lists the assistants that connected: see Asking first.

    With --remote it serves the assistant from another Mac instead: see From another Mac.

    jevision mcp [--project folder]
jevision mcp --pair link
jevision mcp --remote Mac [--project name]
jevision mcp --forget Mac
    OptionWhat it does
    --project folderProject folder whose tests the assistant may see. Default: the nearest folder at or above the current one that has a .jevision folder, otherwise the current folder. With --remote, the name of the project open in JEVision on that Mac; default: that project, whatever its name.
    --pair linkPairs this computer with a Mac, using the one-time command that Settings → iPhone & Remote → Add → Assistant on another computer shows on that Mac. The code works once, for five minutes.
    --remote MacServes the assistant with the tests of a paired Mac, by its name or the start of its id. The assistant starts this command itself.
    --forget MacRemoves a paired Mac from this computer. To also cut this computer off on the Mac, choose Disconnect there.

    jevision blocks

    Lists, installs, updates and removes the blocks that other people shared in a project, as Install Block… and Custom Blocks… do in the app, and installs the blocks of a project again from jevision.blocks.json. Installed blocks are in the blocks folder of the project.

    jevision blocks list [--project folder]
jevision blocks install source [--only id,…] [--yes] [--force] [--project folder]
jevision blocks update [id] [--yes] [--force] [--project folder]
jevision blocks remove id [--force] [--project folder]
jevision blocks restore [--only id,…] [--yes] [--force] [--project folder]
    CommandWhat it does
    listPrint the installed blocks: id, version, name and author, and the address a block was installed from.
    install sourceRead a block and print what it does. source is a block folder, a .zip file, or an https address of a GitHub repository, a folder in one, a GitHub release or a .zip file. A source can hold several blocks; then all of them are read and installed. Nothing is installed without --yes.
    update [id]Fetch the address a block was installed from again, and print what changed. Without an id, every block that has an address. Installs the new version with --yes.
    remove idRemove a block. A block that tests or other installed blocks use is not removed unless you add --force; the message names them.
    restoreInstall the blocks that jevision.blocks.json lists and the project doesn't have, or has in another version: see Installing a project's blocks again. Prints the plan; installs it with --yes.
    OptionWhat it does
    --project folderThe project to work in. Default: the nearest folder at or above the current one that has a .jevision folder, otherwise the current folder.
    --only id,…With install and restore: work on these blocks only, with the blocks they need. Ids are separated by commas; an id the source or the list doesn't have is an error.
    --yesInstall after printing what the blocks do. For people who have read it, and for scripts.
    --forceInstall the same version again, or an older one over a newer one; install a new version of a block that another installed block needs in another version; with restore, install a block whose version at its address isn't the one in jevision.blocks.json; or remove a block that tests or other blocks use.

    Without --yes, install prints the block's name, version, author and license, then What it does: with a numbered line for each step. Steps that run a script, send a request, read a database, open apps or files, type on the keyboard or use the clipboard are repeated under Needs your attention:, grouped by kind and with exactly what they do, such as the whole script. It ends with Not installed: add --yes to install it. and the exit status 1.

    A source with several blocks prints each of them this way, in the order they would be installed: the blocks that others need come first. A block that needs one that is neither installed in a version that fits nor in the source stops the installation, with the command that installs it:

    Package: com.acme.messages needs the block com.acme.sign-in ^1.2.0, which isn't installed; install it with `jevision blocks install https://github.com/acme/blocks/tree/main/blocks`.

    Without --yes, restore prints, for each block to install again, what it found at the address (ready, another version, missing there, or the address can't be reached), and for the blocks it would install, What it does: as install does. It installs nothing, ends with Not installed: add --yes to install it. and the exit status 1. With --yes it installs the blocks that are ready, the blocks they need first; a block in another version also needs --force. When the project has everything already, it prints Everything in jevision.blocks.json is installed already. with the exit status 0.

    jevision blocks install https://github.com/acme/sign-in-block
jevision blocks install https://github.com/acme/sign-in-block --yes
jevision blocks list
jevision blocks install https://github.com/acme/blocks/tree/main/blocks
jevision blocks update --yes
jevision blocks remove com.acme.sign-in
jevision blocks restore --yes

    A test that needs a block you haven't installed says so in jevision validate and jevision run, with the id and version the test was made with and the command that installs it, such as needs the block com.acme.sign-in 1.2.0 … install it with `jevision blocks install https://github.com/acme/sign-in-block`. A test that knows no address says jevision blocks install <folder, .zip file or https address>.

    Exit status: 0, done (or nothing to do); 1, a block wasn't installed because --yes is missing, --force is needed (to go back to an older version, to update a block that another one needs in another version, or to restore a block whose version changed), a block it needs is missing, or the block has an error; a block that is installed already in the same version is left as it is, with status 0; 2, wrong arguments, a source that can't be read or downloaded, or a block that isn't installed.

    jevision schedule run

    Runs the schedules of a project that are due now. The app sets up macOS to start this command at the right times, so you don't need to run it yourself.

    jevision schedule run project

    A schedule is due once for its latest time since the last check, even when the Mac slept through it, unless that time is more than 12 hours ago. When the screen is locked, nobody is logged in, or macOS hasn't allowed jevision to record the screen and control the computer, the run is skipped and nothing is clicked or typed.

    Exit status: 0, nothing was due or all tests passed; 1, a test failed or a run was skipped; 2, the project or its schedule file couldn't be read, or a run couldn't start.

    What a Mac needs to run tests

    Before running anything, jevision run checks that the Mac can run tests, and if not, says what to do and exits with status 2. A Mac can run tests when:

    • a user is logged in and jevision runs in that user's session: from Terminal, from a CI agent started in that session, or over SSH as that same user while they stay logged in at the screen, as in a virtual machine; not as a system service;
    • the screen is unlocked;
    • the app jevision runs in (Terminal, your editor or your CI agent) is allowed under Screen & System Audio Recording and Accessibility. The message names that app and the lists to turn it on in. See Permissions.

    Running in CI

    Tests need a real screen with a logged-in user, so cloud-hosted CI runners can't run them. Use a Mac of your own as a runner. For GitHub Actions, set up a self-hosted runner and install it as a service with ./svc.sh install while logged in as the user who runs the tests. On macOS this makes a launch agent that runs in that user's session. Then allow Screen Recording and Accessibility for the program the first run names.

    jobs:
  ui-tests:
    runs-on: [self-hosted, macOS]
    steps:
      - uses: actions/checkout@v4
      - name: Check test files
        run: jevision validate tests && jevision fmt --check tests
      - name: Run UI tests
        env:
          ACME_PASSWORD: ${{ secrets.ACME_PASSWORD }}
        run: jevision run tests --junit junit.xml --html reports
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: jevision-reports
          include-hidden-files: true
          overwrite: true
          path: |
            junit.xml
            reports/
            tests/.jevision/runs/

    Secrets go in as environment variables named like the secret, here ACME_PASSWORD for ${secret.ACME_PASSWORD}.

    The app can write the workflow for you: Settings → Advanced → Continuous Integration → Add to Project…. It shows the file first, with the secrets your tests use, and saves it as .github/workflows/jevision.yml at the top of the git repository your project is in. It replaces an existing file only after you confirm, and it doesn't commit or push anything.

    CI runs in the app

    The artifact jevision-reports also carries the run reports, with their screenshots, from .jevision/runs. In a CI job, jevision run writes where the run came from into each report: the CI system, the repository, the branch, the commit, the pull request and the page of the run. GitHub Actions, GitLab CI, Buildkite, CircleCI and Jenkins are recognized.

    When you are signed in to GitHub (Settings → Git and GitHub) and the project's repository is on GitHub, the app fetches the artifacts of the newest runs each time you open Runs, and when you click the refresh button above the list. It adds the runs to the project's history, each artifact once, even if you fetch again or delete a run. They are marked CI · pull request #482 or CI · branch main, and the report links to the run on GitHub. The filter above the list (This Mac, Schedule, iPhone, CI) shows only the runs started that way. Without a sign-in nothing is fetched, and the CI filter says how to sign in. The sign-in is kept in the Keychain and is never written to the project or to a log.

    An artifact is at most 512 MB, and the app looks at the 20 newest. Artifacts of an older workflow, which was named ui-test-reports and had no run reports, aren't read: add the workflow to the project again.

    To be told in Slack, Telegram or email when the run fails, set up Notifications in the app and commit jevision.notifications.json; jevision run sends one summary when it finishes, and on CI reads the secrets from environment variables.
