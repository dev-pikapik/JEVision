    Environments and secrets

    Run the same test against staging, production or a local server, and keep passwords and keys out of test files.

    On this page

    Environments

    An environment is a named set of values that differ between the places you test: a server address, a user name, a language. Your tests read the values by name, so one test runs anywhere: pick staging today and production tomorrow without changing the test.

    The environments file

    Environments live in jevision.environments.json in the project folder, next to the tests, and are committed with them:

    {
  "format": 1,
  "default": "staging",
  "environments": {
    "production": { "BASE_URL": "https://example.com" },
    "staging": { "BASE_URL": "https://staging.example.com", "USER": "qa" }
  }
}
    • format is 1.
    • environments maps each environment's name to its values. Environment names use letters, digits, - and _. Value names start with a letter or _ and use letters, digits and _. Values are text.
    • default is optional and must name one of the environments. It is used when you don't choose one.

    JEVision finds the file in the nearest folder at or above the tests that has the file or a .jevision folder.

    Never put secrets in this file. It is committed with your tests and everyone with the repository can read it. Use secrets for passwords, tokens and keys.

    Using values in a test

    Write ${env.NAME} where the value should go:

    { "type": "openFile", "files": ["${env.BASE_URL}/sign-in"], "next": "email" }
{ "type": "type", "text": "${env.USER}", "into": { "image": "refs/user-field.png" }, "next": "password" }

    Placeholders work in the text of a type block and in the paths and addresses of files a block opens or reads. See Placeholders.

    The editor and jevision validate report a name that no environment has as an error, and a name that only some environments have as a warning, listing the environments that lack it.

    Choosing an environment

    • In the app: pick the environment at the foot of the sidebar or in the Run menu. The choice is kept per project on this Mac. The app starts with the file's default until you choose another one.
    • On the command line: jevision run tests/ --env staging. Without --env, the file's default is used.
    • For an AI assistant: the env argument of run_test.
    • For a schedule: its environment. See Schedules.

    Before a run, the app lists the names of values and secrets that are missing, never the values. The report says which environment the run used.

    Secrets

    A secret is a value that must never be written in a file: a password, a token, a key. A test refers to it by name, as ${secret.NAME}:

    { "type": "type", "text": "${secret.ACME_PASSWORD}", "into": { "image": "refs/password-field.png" } }
    • When you record and type into a password field, JEVision turns what you typed into a secret, saves it in the Keychain and writes only its name in the test.
    • Secret values are never shown, printed or written to reports, where they are masked. AI assistants see only ${secret.NAME}.
    • A secret can differ per environment: the app saves it in the Keychain for the environment chosen when you set it.

    Where a secret's value comes from

    At run time, JEVision looks for the value of ${secret.NAME} in this order and takes the first it finds:

    1. the environment variable NAME, which is how CI systems pass secrets;
    2. the Keychain item of the chosen environment;
    3. the Keychain item shared by all environments.

    The first time jevision reads a Keychain item, macOS may ask whether to allow it. For runs nobody watches, such as schedules and CI, choose Always Allow.

    # In CI, pass the secret as an environment variable:
ACME_PASSWORD="$ACME_PASSWORD" jevision run tests/ --env staging
