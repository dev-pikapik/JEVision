    Notifications

    Get a message in Slack, Telegram or email when a test fails or passes again, so a run nobody watches doesn't stay unnoticed.

    Set up

    Open a project, choose JEVision → Settings → Notifications, and turn on one or more channels: Post to Slack, Post to Telegram or Send email. Each channel has its own Send a message choice, so a busy team channel can hear about every change while your own inbox only hears about failures. Send Test Message saves the settings and sends a short message, to check that the channel works before a real run needs it.

    The settings are saved in jevision.notifications.json in the project folder and committed with the tests, so everyone who runs them sends the same messages. The webhook, bot token and mail password are never written there: they stay in the Keychain on this Mac, and JEVision never shows them again. See On CI for where they come from on a runner.

    When a message is sent

    Each channel sends a message in one of four cases:

    Choice in the appwhen in the fileA message goes out
    When a test fails"failed"When a test fails, every time it does.
    When a test fails or passes again"failedOrFixed"When a test fails, and when a test that failed in its run before passes again. The default.
    When a test starts or stops failing"changed"When a test that wasn't failing fails, and when a failing test passes again. A test that keeps failing says nothing more, so a broken test doesn't fill the channel every night.
    After every run"every"After every run that finished, passed or failed.

    “The run before” is the last earlier run of the same test file that finished, in this project's run history. Runs that were stopped or blocked don't count, because they don't say whether the test was passing. The history is the .jevision/runs folder of the project. A CI job usually starts from a fresh copy of the repository without that folder, so JEVision also keeps the last result of each test in a small file and looks there when the history has no earlier run. Keep that file from one CI run to the next, as Keeping the last results between CI runs shows; without it, every failure on CI counts as new and nothing counts as fixed.

    These rules hold for every choice:

    • A stopped run sends nothing, and neither does a batch of runs with a stopped run in it.
    • A test that didn't run because a test it depends on failed says nothing of its own, since the test that failed does; with After every run it is reported as Blocked. A test blocked by a dependency that doesn't exist or that depends on itself in a circle is reported like a failure.
    • A failure in quarantine doesn't count as a failure. The test still runs, and After every run still reports it.
    • Only for scheduled runs and CI keeps runs you start yourself in the app or in a terminal quiet. Scheduled runs and runs where the environment variable CI is set (GitHub Actions and most CI systems set it) still send.

    One summary for many tests

    Run All in the app, jevision run with several tests, and every schedule that runs several tests send one message when the last test is done, not one per test. The title says how it went:

    • Failed: 3 of 42 tests: the tests that failed, with a sentence each;
    • Blocked: 1 of 42 tests: a test didn't run because a test it depends on failed or couldn't run;
    • Fixed: 2 tests passing again;
    • Passed: 42 tests.

    A summary names at most 10 failed tests and says how many more there were. A test run on its own sends its own message, titled like Failed: Sign in. Whether a channel gets the message depends on its choice above: with When a test fails a batch where everything passed sends nothing at all.

    What a message says

    • how it went, in the title: Failed, Fixed, Passed or Blocked, and the test's name;
    • why a test failed, in one sentence, such as which step and what it expected;
    • how long the run took, the test file, the schedule and the environment;
    • where the report is: a link to the GitHub Actions run when the tests ran on one, otherwise the folder on the Mac that ran them. Reports stay on that Mac, so nothing but the message goes to the service.

    Pictures only ever come from the report, where the areas you hide and password fields are already covered. See Screenshots and privacy.

    Slack

    1. In Slack, open api.slack.com/apps and create an app. Turn on Incoming Webhooks, add a webhook for the channel and copy its URL, which starts with https://hooks.slack.com/.
    2. In JEVision, turn on Post to Slack, click Set… by Webhook and paste the URL.

    Messages are laid out with Slack's blocks: a heading in the title, the facts side by side, the failed tests as a list and the report below. A plain-text version goes with them for notifications and screen readers. If Slack refuses the layout, JEVision sends the plain text instead, so the message still arrives.

    Telegram

    1. In Telegram, write to @BotFather to make a bot and copy its token.
    2. In JEVision, turn on Post to Telegram, click Set… by Bot token and paste the token.
    3. Write something to the bot, or add it to the group or channel and send a message there. In JEVision, click Find Chat: it lists the chats the bot has seen, the latest first, and Use fills in the chat for you.

    You can also type the chat's ID yourself: a number such as -1001234567890 for a group, or @name for a public channel.

    Find Chat needs the bot to have been written to lately; Telegram forgets old messages. It doesn't work for a bot that hands its messages to a webhook, and says so: make a new bot just for JEVision, or type the ID.

    Email

    Mail goes through an SMTP server of your own, such as the one of your mail provider. Fill in:

    • Mail server and Port, such as smtp.gmail.com and 465;
    • Encryption: TLS (usually with port 465) or STARTTLS (usually with 587). Mail is never sent unencrypted, and a server that can't upgrade to STARTTLS is refused;
    • User name and Password, unless the server takes mail without signing in; for Gmail and iCloud Mail, make an app password in your account's security settings;
    • From, such as JEVision <qa@example.com>, and To, one address or several.

    The mail has a plain-text part and a formatted part with a coloured heading, the facts and the failed tests. When a test failed, the formatted part also shows a screenshot of the step where it failed, with private areas covered. It is part of the mail itself, so it shows even when the mail program blocks pictures from the web. Screenshots over 5 MB are left out.

    The settings file

    {
  "format": 2,
  "unattendedOnly": true,
  "slack": { "when": "failedOrFixed" },
  "telegram": { "chat": "-1001234567890", "when": "changed" },
  "email": {
    "server": "smtp.gmail.com", "port": 465, "security": "tls",
    "user": "qa@example.com", "from": "JEVision <qa@example.com>",
    "to": ["team@example.com"], "when": "failed"
  }
}
    FieldRequiredValue
    formatYes2. A file of format 1 is still read. See below.
    unattendedOnlyNotrue to tell only about scheduled runs and CI. Default: false.
    slackNo{ "when": … }. Leave it out to turn Slack off.
    telegramNo{ "chat": "…", "when": … }. chat is required and can't be empty.
    emailNoserver, port, from and to (at least one address) are required. security is "tls" (the default) or "startTls". user is left out for a server that takes mail without signing in.
    when, in each channelNo"failed", "failedOrFixed" (the default), "changed" or "every".

    Unknown keys are an error, so a typo doesn't go unnoticed, and so is an address that isn't an address. Turning every channel off in the app removes the file. The secrets are not in it.

    Files from before format 2

    Format 1 had one "when" for the whole file and "slack": true or false. JEVision still reads it: the one when becomes the choice of every channel, "slack": true becomes { "when": … }, and false turns Slack off. Nothing is rewritten until you save the settings in the app, which writes format 2. A JEVision from before format 2 refuses the file, as it does any newer format.

    On CI

    A runner has no Keychain to read, so the secrets come from environment variables instead. A variable wins over the Keychain.

    ChannelEnvironment variable
    SlackJEVISION_SLACK_WEBHOOK, the webhook URL
    TelegramJEVISION_TELEGRAM_TOKEN, the bot token
    EmailJEVISION_SMTP_PASSWORD, the mail password
     
    - name: Run UI tests
  env:
    JEVISION_SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK }}
  run: jevision run tests

    jevision run sends the messages when it finishes and says how each went (Message sent to Slack, or why not). A message that couldn't be sent never changes the exit status. Add --no-notify to run without sending anything. On GitHub Actions the message links to the run, where the reports can be uploaded as artifacts. See Running in CI.

    Keeping the last results between CI runs

    To say that a test is fixed, or to stay quiet while a test keeps failing, JEVision has to know how each test did last time. On your Mac it reads the run history. A CI job usually starts from a fresh copy of the repository, where that history is gone, so every run that passes or fails also writes the result into one small file in the project folder: .jevision/last-results.json. It says, for each test file, whether its last run passed or failed, and nothing else. All a CI job has to do is bring this file back before the tests run and keep it after they finish, also when they fail. Leave it out of git, like the rest of .jevision: CI doesn't commit what a run changes, so a committed copy would never move on.

    Name the project folder when you run the tests, as jevision run --project tests tests does below. Without it, a fresh copy, which has no .jevision folder yet to show where the project starts, can make the run keep the file at the top of the repository instead, where the CI never looks for it.

    GitHub Actions. The workflow that Settings → Advanced → Continuous Integration → Add to Project… writes does this for you with GitHub's cache. A workflow added before doesn't: add it again, or put these two steps around the step that runs the tests, with your project folder in path:

    - name: Restore the last result of each test
  uses: actions/cache/restore@v4
  with:
    path: |
      tests/.jevision/last-results.json
    key: jevision-last-results-${{ github.run_id }}-${{ github.run_attempt }}
    restore-keys: jevision-last-results-
- name: Run UI tests
  run: jevision run --project tests tests
- name: Save the last result of each test
  if: always()
  uses: actions/cache/save@v4
  with:
    path: |
      tests/.jevision/last-results.json
    key: jevision-last-results-${{ github.run_id }}-${{ github.run_attempt }}

    GitHub keeps each cache for the branch that saved it. A run of a pull request finds the results of the pull request's own earlier runs, and those of the branch it goes into and of the default branch, but never those of another pull request. The workflow runs only for pull requests and when started by hand, so the branches it goes into have no results of their own, and the first run of each pull request starts with none: every test that fails is reported as a new failure, even one that was already failing, and no test is reported as fixed. From the second run on, the pull request compares with its own last run.

    To compare the first run of a pull request with your default branch instead, run the tests on that branch too: add a push trigger for it, and each push keeps the results for the pull requests that follow. Starting the workflow by hand on that branch does the same once.

    on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

    GitLab CI. Add the file to the cache of the job that runs the tests. when: always keeps it after a failed run too; without it GitLab keeps the cache only when the job passes. Each branch has its own results and starts from those of the default branch:

    ui-tests:
  script:
    - jevision run --project tests tests
  cache:
    key: jevision-last-results-$CI_COMMIT_REF_SLUG
    fallback_keys:
      - jevision-last-results-$CI_DEFAULT_BRANCH
    paths:
      - tests/.jevision/last-results.json
    when: always

    Jenkins. Jenkins keeps the workspace between builds unless the job cleans it, and then the run history is still there and nothing more is needed. If the job starts from a clean workspace, run the tests with the script below.

    Buildkite and any other CI. The tests run on a Mac you set up, so the file can wait for the next run in a folder on that Mac, outside the copy of the repository. Save these lines in the repository, for example as ui-tests.sh, and make the CI run sh ui-tests.sh instead of jevision run. Change tests to your project folder and my-app to a name of your own, one per project:

    kept="$HOME/jevision-kept/my-app"
mkdir -p "$kept" tests/.jevision
cp "$kept/last-results.json" tests/.jevision/ 2>/dev/null || true
status=0
jevision run --project tests tests || status=$?
cp tests/.jevision/last-results.json "$kept/" 2>/dev/null || true
exit $status

    If the jobs of one project can run on different Macs, use the cache or artifacts of your CI the same way instead: bring .jevision/last-results.json back before the tests run and keep it after they finish, whatever the result.

    When a message doesn't arrive

    • “… isn't on this Mac”. The webhook, token or password is missing: click Set… in the settings, or set the environment variable.
    • Nothing arrives and nothing is said. The choice of Send a message doesn't ask for this run: a run where everything passed sends nothing unless the choice is After every run. Check Only for scheduled runs and CI as well.
    • Slack says no. The webhook was deleted or its app removed from the channel: make a new one.
    • Telegram says the chat wasn't found. Add the bot to the group or channel (a channel needs it as an administrator who can post), then use Find Chat again.
    • Mail is refused. The message says whether the user name or password was wrong or the secure connection couldn't be made. Check the port against the encryption, and use an app password where the provider asks for one.

    For a Mac that runs schedules unattended, see Preparing a Mac for runs nobody watches.
