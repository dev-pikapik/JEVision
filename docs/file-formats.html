    File formats

    Everything JEVision keeps is plain text or ordinary images in your project folder, so you can read it, review it in git and edit it by hand.

    Files in a project

    FileWhat it holdsIn git
    *.flow.jsonOne test eachYes
    Images, such as refs/inbox.pngReference images and the pictures of click targetsYes
    *.csvTables for data-driven testsYes
    jevision.environments.jsonEnvironmentsYes
    jevision.project.jsonRetries and quarantine for the whole projectYes
    jevision.schedule.jsonSchedulesYes
    .jevision/runs/Reports, screenshots and videos of runsNo
    .jevision/schedule-history.jsonWhat came of scheduled runs on this MacNo

    Secrets are in none of these files. They live in the Keychain or in environment variables. See Secrets.

    Test files

    A test is a JSON file whose name ends in .flow.json. It is UTF-8 text with the test's fields at the top and its blocks in blocks:

    {
  "format": 1,
  "name": "Save a note",
  "app": "com.apple.TextEdit",
  "start": "open",
  "blocks": {
    "open": { "type": "openApp", "next": "new" },
    "new": { "type": "pressKeys", "keys": "cmd+n", "next": "hello" },
    "hello": { "type": "type", "text": "Hello", "next": "saved" },
    "saved": {
      "type": "check",
      "reference": { "image": "refs/hello.png", "compare": "similar", "threshold": 0.95 }
    }
  },
  "canvas": {
    "positions": { "open": { "x": 0, "y": 0 }, "new": { "x": 0, "y": 120 } }
  }
}

    Every field and block type is described in Writing tests. A field JEVision doesn't know is an error rather than being ignored, so a typo never goes unnoticed. JEVision saves tests in canonical form; jevision fmt does the same for files edited by hand.

    The canvas

    The optional canvas field keeps how the test looks in the editor. It never changes what a run does.

    FieldValue
    positionsWhere each block sits: block id → { "x": …, "y": … }, the top-left corner of the block in canvas points from the top-left corner of the canvas. Without positions, the editor lays out every block itself.
    sectionsTitled frames that group blocks: section id → { "title": "…", "frame": { "x": …, "y": …, "width": …, "height": … } }.
    notesSticky notes: note id → { "text": "…", "author": "…", "time": "…", "frame": { … } }. author and time (an RFC 3339 date and time, such as 2026-10-18T09:30:00Z) are optional.

    Whole numbers are written without a decimal point, so moving a block by a whole point changes one short line in the diff.

    Reference images

    References and click targets are PNG images of part of the app's window, saved by the app next to the tests, usually in a refs folder. A reference for dark appearance has the same name with .dark before .png, such as refs/inbox.dark.png. See Dark appearance. Paths in tests are relative to the test file and use /.

    Environments

    jevision.environments.json, in the project folder:

    {
  "format": 1,
  "default": "staging",
  "environments": {
    "staging": { "BASE_URL": "https://staging.example.com" }
  }
}

    See The environments file for the rules.

    Project settings

    jevision.project.json, in the project folder, optional:

    {
  "format": 1,
  "retries": 2,
  "quarantine": [ { "test": "checkout/pay.flow.json", "reason": "Issue #42" } ]
}

    See Project settings file.

    Schedules

    jevision.schedule.json, in the project folder:

    {
  "format": 1,
  "schedules": [
    { "name": "Nightly", "tests": "all", "repeat": "daily", "at": "03:00" }
  ]
}

    See The schedule file for every field.

    Data tables

    CSV files as spreadsheet apps export them: a header line with the column names, then one line per row. See CSV rules.

    Run reports

    Every run saves report.json in its folder under .jevision/runs, next to its screenshots. Paths inside it are relative to that folder unless noted. The main fields:

    FieldValue
    format1
    test, file, appThe test's name, its file (relative to the project folder) and the bundle id of the app under test
    startedAt, durationMsWhen the run started (UTC, RFC 3339) and how long it took, in milliseconds
    verdictpassed, failed or cancelled: the result of the last attempt
    flakytrue when the attempts disagreed: a failure followed by a pass, or failures that differed
    baselinesCreatedReferences this run saved because they didn't exist yet, relative to the project folder
    requestedByThe paired device that started the run from afar, such as an iPhone; absent for a run started on the Mac
    scheduleThe schedule that started the run; absent for a run someone started
    environmentThe environment the run used; absent when it used none
    videoThe run's video; absent when none was kept
    fileHashA fingerprint (SHA-256) of the test file, which tells runs of the same test apart from runs after it changed
    quarantined, quarantineReasonWhether the test was in quarantine, and why
    attemptsEvery attempt: number, verdict, durationMs, failure, the data row for a data-driven test, and its steps

    Each step has seq, test, block, type, status (passed, failed, baselineCreated or cancelled) and durationMs. Depending on the block it also has screenshots before and after, the reference compared with, the expected copy of it, a diff picture, the similarity from 0 to 1, the AI model's answer in vision, the branch an if block took, a failure, and videoAtMs, when the step starts in the video. A failure has a code and params; the app and the command line turn them into a sentence.

    Schedule history

    .jevision/schedule-history.json keeps the newest 200 scheduled runs on this Mac, oldest first. checkedAt is the minute the schedules were last checked, counted in local time from the start of 1970:

    {
  "checkedAt": 29483460,
  "runs": [
    { "schedule": "Nightly", "startedAtMs": 1792292400000, "durationMs": 81000,
      "outcome": { "result": "finished", "passed": 11, "failed": 1 } },
    { "schedule": "Smoke", "startedAtMs": 1792314300000, "durationMs": 0,
      "outcome": { "result": "skipped", "reason": "screenLocked" } }
  ]
}

    result is finished (with the numbers of tests that passed and failed), skipped (with reason screenLocked, noUser or notAllowed) or error (with a message). If the file can't be read, it starts over: it is only a record and never stops schedules.

    Format versions

    Every JSON file JEVision writes starts with "format": 1. When a format changes in a way older versions can't read, the number goes up. A JEVision that finds a newer format than it knows refuses the file with “format 2 is from a newer JEVision”, rather than misreading it or overwriting what it doesn't understand.
