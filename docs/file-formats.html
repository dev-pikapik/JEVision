    File formats

    Everything JEVision keeps is plain text or ordinary images in your project folder, so you can read it, review it in git and edit it by hand.

    Test files

    A test is a JSON file whose name ends in .flow.json. It is UTF-8 text with the test's fields at the top and its blocks in blocks:

    {
  "format": 1,
  "name": "Save a note",
  "app": "com.apple.TextEdit",
  "start": "open",
  "blocks": {
    "open": { "type": "openApp", "next": "new" },
    "new": { "type": "pressKeys", "keys": "cmd+n", "next": "hello" },
    "hello": { "type": "type", "text": "Hello", "next": "saved" },
    "saved": {
      "type": "check",
      "reference": { "image": "refs/hello.png", "compare": "similar", "threshold": 0.95 }
    }
  },
  "canvas": {
    "positions": { "open": { "x": 0, "y": 0 }, "new": { "x": 0, "y": 120 } }
  }
}

    Every field and block type is described in Writing tests. A field JEVision doesn't know is an error rather than being ignored, so a typo never goes unnoticed. JEVision saves tests in canonical form; jevision fmt does the same for files edited by hand.

    The canvas

    The optional canvas field keeps how the test looks in the editor. It never changes what a run does.

    FieldValue
    positionsWhere each block sits: block id → { "x": …, "y": … }, the top-left corner of the block in canvas points from the top-left corner of the canvas. Without positions, the editor lays out every block itself.
    sectionsTitled frames that group blocks: section id → { "title": "…", "frame": { "x": …, "y": …, "width": …, "height": … } }.
    notesSticky notes: note id → { "text": "…", "author": "…", "time": "…", "frame": { … } }, with more fields for what a note is about, its files and links, and the talk under it; see Notes. author and time (an RFC 3339 date and time, such as 2026-10-18T09:30:00Z) are optional.

    Whole numbers are written without a decimal point, so moving a block by a whole point changes one short line in the diff.

    Notes

    A note is Markdown text with a place on the canvas. Every field except text and frame is optional, and a file written before they existed opens as it was.

    FieldValue
    textThe note as Markdown source: headings, lists, check boxes, quotes, links, bold and italic text. @name mentions a person; the editor suggests the names of the project's git authors. The text is kept as it was written; the editor only draws the styles.
    anchorWhat the note is about. { "type": "block", "block": "block id" } for a block, { "type": "folder" } for the folder the test is in, and for the test itself, the default, no anchor. A note about a block shows in that block's inspector, moves with the block and is copied with it, without its replies and files. A note about a folder shows on the folder's page.
    attachmentsA list of what comes with the note: { "file": "shot.png" } for a file kept next to the test (see below), { "link": "https://…" } for a web address. A link to a GitHub issue or pull request shows its number, title and state once you are signed in to GitHub.
    repliesThe talk under the note, in order: { "id": "…", "author": "…", "time": "…", "text": "…" }. The reply id is unique within the note.
    resolved{ "by": "…", "time": "…" } when the discussion is settled; left out while it is open. The canvas can hide settled notes.
    frameWhere the note is and how big it is, as for a section.

    The files of a note are copied next to the test: the files of the notes of login/sign-in.flow.json are in login/sign-in.assets/notes/note id/. Renaming the test in JEVision moves the folder with it, and deleting the test moves it to the trash too. A file bigger than the limit set in Settings (10 MB by default) is not attached silently: JEVision offers to track it with Git LFS, which adds a line to .gitattributes only when you choose it, or to attach it anyway.

    The history of a note comes from the git history of the test file, so who wrote it, edited it, replied or settled it is shown without anything stored in the note. In a project without git, the note shows only its author and time.

    Two people who changed the same test combine their notes: replies and files that one side added are kept, a reply or file that one side removed and the other left alone is removed, and the same reply edited two ways is left for a person to settle.

    Custom blocks and packages

    A custom block is a test that other tests run with a runTest block, which may give it values in inputs. There are two kinds of files:

    • blocks/Name.block.json, a block you made. It is a test file in every way (see Test files) that reads its values as ${input.NAME}, and isn't run on its own.
    • blocks/id.jevblock/, a package from someone else: a folder with block.json (who made it, its version, its inputs and the packages it needs), flow.json (the steps, a test file) and the pictures the steps use.
    {
  "format": 1,
  "id": "com.acme.sign-in",
  "name": "Sign in",
  "version": "1.2.0",
  "author": "Acme QA",
  "license": "MIT",
  "inputs": [ { "name": "email" }, { "name": "password" } ],
  "dependencies": [ { "id": "com.acme.open-app", "version": "^1.0.0", "source": "https://github.com/acme/open-app" } ]
}

    dependencies lists the other packages the steps run, up to 50. Each entry has an id; a version, the range of versions that work, such as ^1.0.0, ~1.2.0, 1.x or >=1.2.0 <2.0.0, and * (any version) when left out; and a source, an https address to install the package from when it is missing. Every range is explained in Version ranges.

    Paths in a package are relative to its flow.json and stay in its folder. The one exception is a runTest step that runs a listed package: installed packages sit side by side, so its test is ../id.jevblock/flow.json. A step that runs a package that isn't listed is an error, and so is any other path with ...

    jevision.blocks.json, in the project folder, keeps the address each package was installed from in sources, and the version installed from it in versions, so that jevision blocks restore can install the same ones again:

    {
  "format": 1,
  "sources": {
    "com.acme.sign-in": "https://github.com/acme/sign-in-block"
  },
  "versions": {
    "com.acme.sign-in": "1.2.0"
  }
}

    Ids are in alphabetical order, so git shows clean differences. Packages installed from a file have no entry. A file without versions, from an older JEVision, still reads; its packages count as installed in any version.

    A runTest block that runs a package keeps "package": { "version": "1.2.0", "source": "https://github.com/acme/sign-in-block" }, the version the test was made with and, when there is one, the address to install it from. Both are optional, and a test without package reads as before. When the package isn't installed, validation and runs name it with that version and say how to install it.

    See The package format for every field and rule of block.json. Its JSON Schema is part of this documentation.

    Reference images

    References and click targets are PNG images of part of the app's window, saved by the app next to the tests, usually in a refs folder. A reference for dark appearance has the same name with .dark before .png, such as refs/inbox.dark.png. See Dark appearance. Paths in tests are relative to the test file and use /. A picture named by a variable, such as { "image": "${var.shot}" }, is a PNG the run made or found, wherever it is on the Mac, and has no .dark version. See Target.

    Environments

    jevision.environments.json, in the project folder:

    {
  "format": 1,
  "default": "staging",
  "environments": {
    "staging": { "BASE_URL": "https://staging.example.com" }
  }
}

    See The environments file for the rules.

    Project settings

    jevision.project.json, in the project folder, optional:

    {
  "format": 1,
  "retries": 2,
  "quarantine": [ { "test": "checkout/pay.flow.json", "reason": "Issue #42", "until": "2026-11-03" } ],
  "suggestQuarantineAfter": 3,
  "localOnly": true,
  "cleanHome": true,
  "hide": [ { "x": 0.7, "y": 0, "width": 0.3, "height": 0.08 } ],
  "ai": {
    "screen": { "provider": "ollama", "model": "qwen2.5vl:7b" },
    "text": { "provider": "anthropic" }
  }
}
    • format is 1. A file from a newer JEVision is refused instead of being misread.
    • retries (optional), 0 to 10, quarantine (optional; each entry has a test, and optionally a reason and the last day until as YYYY-MM-DD) and suggestQuarantineAfter (optional, 1 to 10, default 3): see Project settings file.
    • localOnly (optional, false when left out): true sends the project's screenshots only to AI models on this Mac, and never to assistants.
    • cleanHome (optional, false when left out): true starts the app of an openApp block with "resetState": true as on its first launch: with an empty home folder of its own, which the run deletes when it ends, and none of the app's settings. The run saves the app's settings in ~/Library/Application Support/JEVision/Saved app settings before clearing them and puts them back once the app has quit; if the run crashes, or the app is still open when it ends, they go back at the next run or the next launch of JEVision. The person's own files are never touched. Not reset: passwords in the Keychain, the list of recent documents and what the app keeps on its servers or in iCloud. Apps in the macOS sandbox keep their data where macOS puts it, so for them only the windows from last time are left out, and the step says so. See openApp.
    • ai (optional): the AI the project asks, instead of the one chosen in each person's Settings → AI. screen is for checks by meaning, text for drafting tests and explaining failures. Each has a provider, one of anthropic, openai, gemini, jev, ollama, lmstudio or openai-compatible (not jev for text), and an optional model that, when left out, is the model chosen for that provider in Settings. A check that names its own provider or model comes first. The file never holds an API key or an address. See Which AI answers.
    • hide (optional): areas of the window, as x, y, width and height in fractions from 0 to 1 from its top-left corner, painted over in grey in every screenshot before it is saved in a report or sent to an AI model or an assistant. Each area must have a size and end inside the window.

    Unknown keys are an error, so a typo doesn't go unnoticed. See Screenshots and privacy.

    Schedules

    jevision.schedule.json, in the project folder:

    {
  "format": 1,
  "schedules": [
    { "name": "Nightly", "tests": "all", "repeat": "daily", "at": "03:00" }
  ]
}

    See The schedule file for every field.

    Notifications

    jevision.notifications.json, in the project folder:

    {
  "format": 2,
  "slack": { "when": "failedOrFixed" },
  "telegram": { "chat": "-1001234567890", "when": "changed" }
}

    Each channel has its own when. The webhook, bot token and mail password are never in the file. A file of format 1 is still read. See The settings file for every field.

    Data tables

    CSV files as spreadsheet apps export them: a header line with the column names, then one line per row. See CSV rules.

    Run reports

    Every run saves report.json in its folder under .jevision/runs, next to its screenshots. Paths inside it are relative to that folder unless noted. The main fields:

    FieldValue
    format1
    test, file, appThe test's name, its file (relative to the project folder) and the bundle id of the app under test
    startedAt, durationMsWhen the run started (UTC, RFC 3339) and how long it took, in milliseconds
    verdictpassed, failed or cancelled: the result of the last attempt
    flakytrue when the attempts disagreed: a failure followed by a pass, or failures that differed
    baselinesCreatedReferences this run saved because they didn't exist yet, relative to the project folder
    requestedByThe paired device that started the run from afar, such as an iPhone; absent for a run started on the Mac
    scheduleThe schedule that started the run; absent for a run someone started
    environmentThe environment the run used; absent when it used none
    videoThe run's video; absent when none was kept
    fileHashA fingerprint (SHA-256) of the test file, which tells runs of the same test apart from runs after it changed
    quarantined, quarantineReasonWhether the test was in quarantine when it ran, and why; a quarantine whose last day was past doesn't count
    virtualMachine, displayScaleWhether the run ran in a virtual machine, and the pixels per point of its display: 2 on Retina, 1 on a standard display; absent when unknown
    attemptsEvery attempt: number, verdict, durationMs, failure, the data row for a data-driven test (its number, label and hash, a fingerprint of its values that tells an edited row from the same row before the edit; reports written before it was kept have no hash), and its steps

    Each step has seq, test, block, type, status (passed, failed, baselineCreated or cancelled) and durationMs. Depending on the block it also has screenshots before and after, the reference compared with, the expected copy of it, a diff picture, the similarity from 0 to 1, the AI model's answer in vision, the branch an if block took (then, elseIf1, elseIf2… or else) with branches, how many ways out it had, and branchCondition, what the condition of the way taken looks for (absent for else and in reports from older versions), a failure, and videoAtMs, when the step starts in the video. A failure has a code and params; the app and the command line turn them into a sentence.

    Schedule history

    .jevision/schedule-history.json keeps the newest 200 scheduled runs on this Mac, oldest first. checkedAt is the minute the schedules were last checked, counted in local time from the start of 1970:

    {
  "format": 1,
  "checkedAt": 29483460,
  "runs": [
    { "schedule": "Nightly", "startedAtMs": 1792292400000, "durationMs": 81000,
      "outcome": { "result": "finished", "passed": 11, "failed": 1 } },
    { "schedule": "Smoke", "startedAtMs": 1792314300000, "durationMs": 0,
      "outcome": { "result": "skipped", "reason": "screenLocked" } }
  ]
}

    result is finished (with the numbers of tests that passed and failed), skipped (with reason screenLocked, noUser or notAllowed) or error (with a message). A damaged file starts over: it is only a record, and damage to it doesn't stop schedules. A file without format is read as format 1, and an older format is upgraded the next time the schedules are checked. A file from a newer JEVision is refused and left as it is, so the newer version still finds everything it wrote: scheduled runs on this Mac wait until JEVision is updated.

    Last results

    .jevision/last-results.json keeps, for each test file, the last run that passed or failed: its folder in .jevision/runs, its verdict, and before, the verdict kept before it. Notifications read it to tell a new failure from an old one where the run history is gone, as in a CI job that starts from a fresh copy of the repository; see Keeping the last results between CI runs. A stopped or blocked run leaves it as it was.

    {
  "format": 1,
  "tests": {
    "login.flow.json": { "run": "20261019-093000-login", "verdict": "failed", "before": "passed" },
    "cart.flow.json": { "run": "20261019-093100-cart", "verdict": "passed" }
  }
}

    If the file can't be read, it starts over: it is only a record and never stops a run. A file without format is read as format 1, and an older format is upgraded when a run saves the file. A file from a newer JEVision is left as it is: this version takes no last results from it and doesn't record its runs in it, so the newer version still finds everything it wrote.

    The app, jevision and the assistant's server may finish runs of the same project at once. Each takes its turn through .jevision/last-results.json.lock beside the file, so no result is lost. The lock file stays; it holds nothing.

    Format versions

    Every JSON file JEVision writes starts with "format" and a number, 1 for all of them except the notification settings, which are at 2 (format 1 is still read). When a format changes in a way older versions can't read, the number goes up. A JEVision that finds a newer format than it knows refuses the file with “format 2 is from a newer JEVision”, rather than misreading it or overwriting what it doesn't understand. The last results are only a record, so a newer one is left alone without a word.

    block.json of a package has a "format" of its own, at 1. A JEVision that finds a newer one refuses the package.

    New blocks and fields that have a default, such as modifiers and button of a drag, modifiers of a hover or scroll, the area target, the clipboard and dateTime blocks with their image, content, language and timeZone, and the types of script inputs and outputs, don't change the number: every test written before they existed still opens and runs, and a field left at its default isn't written. A JEVision older than the feature reports the new field or block as unknown instead of ignoring it.
