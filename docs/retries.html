    Retries, flaky tests and quarantine

    UI tests sometimes fail for reasons that have nothing to do with the app: a slow network, a notification over the window. JEVision helps you tell such failures from real ones.

    On this page

    • Project settings file
    • Retries
    • What the retries tell you
    • Flaky tests from history
    • Quarantine

    Project settings file

    Settings shared by every test of a project go into jevision.project.json in the project folder and are committed with the tests. The file is optional. The app writes it from Settings › Advanced and from the sidebar, so you rarely edit it by hand.

    {
  "format": 1,
  "retries": 2,
  "quarantine": [
    { "test": "checkout/pay.flow.json", "reason": "Payment sandbox is down, issue #42" }
  ]
}
    • format is 1.
    • retries (optional) is the project's default number of retries, 0 to 10.
    • quarantine (optional) lists tests in quarantine: test is a path relative to the project folder, reason is optional.

    Retries

    A failed test can run again a few times before it counts as failed. The number of retries comes from the first of these that is set:

    1. --retries of jevision run, the retries of an assistant's run_test, or the number chosen in the app's Run menu;
    2. the test's own retries;
    3. the project's retries in jevision.project.json.

    Otherwise a test isn't retried. At most 10 retries. In a data-driven test, each row has its own retries.

    What the retries tell you

    A run that needed more than one attempt ends with one sentence about how they went. The report, the app and jevision run all show it:

    • “Passed on retry 1 after failing — the test is flaky.” The app works, but the test doesn't always see it.
    • “Failed 3 times, each time differently — the test may be flaky.” Compare what each attempt saw in the report.
    • “Failed 3 times in a row — a real failure, not flakiness.” Every attempt failed the same way: look for a bug.

    Flaky tests from history

    JEVision also looks back over past runs. When the same test file, unchanged since (the same content), both passed and failed in the same environment over the last 30 days, the app marks it flaky in the sidebar, the project map and the run history, with the dates and counts as evidence. Changing the test starts its record afresh, because a changed test may behave differently.

    Quarantine

    Quarantine is for tests whose failures shouldn't block anyone while they are being fixed, for example while a test server is down.

    • Tests in quarantine still run, and their reports show the failure.
    • Their failure doesn't fail Run All or the exit status of jevision run.
    • The JUnit report lists such a failure as skipped, with the reason and the failure.
    • The sidebar, the project map and the reports mark these tests.

    To put a test in quarantine or release it, use its menu in the sidebar, the test's details, or Settings › Advanced.

    To count their failures like any other, for example in a nightly build, add --include-quarantined-failures:

    jevision run tests/ --include-quarantined-failures

    Quarantine is meant to be short. Give a reason that says what must happen to release the test, such as an issue number.
